# DDSM — Daily · Scan · Delivery

기존 DSD 배송기사 화면과 분리된 간편 배송 앱입니다. 작업 목록은 브라우저에 저장하며, S10의 관리자 엑셀 원본을 로그인한 배송기사 계정으로 건별 조회할 수 있습니다.

- 경로: `/ddsm/` (기존 `/dsd/`는 유지)
- 메인: **D** 날짜/회차, **S** 송장 바코드 스캔, **d** 배송시작
- 스캔: USB/블루투스 키보드형 바코드 리더, 번호 직접 입력, 브라우저 카메라(BarcodeDetector 또는 ZXing CDN 폴백)
- 배송 목록: 수취인/주소/연락처/메모 편집, 지도 검색 열기, 완료·완료취소·삭제
- 각 날짜·회차별 로컬 브라우저 저장, JSON 내보내기/복원
- 소스: `index.html`, `style.css`, `app.js`, `favicon.svg`.

## 중요 제약

인증을 우회하지 않습니다. **가입한 휴대폰 번호와 비밀번호로 로그인해야** S10의 관리자 엑셀에서 운송장번호를 건별 조회할 수 있습니다. **로그인하지 않은 스캔은 등록하지 않습니다.** 기존 로컬 자료 보기는 유지합니다. 작업 결과는 여전히 **localStorage 기반**이므로 기기간 자동 동기화는 없습니다. 브라우저 저장소를 삭제하거나 다른 기기를 쓰면 목록이 보이지 않으며, 백업 JSON에는 수취인 개인정보가 포함될 수 있으므로 안전하게 보관해야 합니다. 여러 탭에서 동시에 편집하면 마지막 저장이 우선될 수 있습니다.

배포는 정적 웹서버가 `/ddsm/` 하위 파일을 서비스하면 가능합니다. GitHub 저장소에 파일을 생성했다고 해서 `llsshh.com/ddsm/`의 서버 경로 설정까지 검증된 것은 아닙니다.

카메라 스캔에는 HTTPS, 카메라 권한이 필요합니다. ZXing CDN을 이용하는 브라우저는 인터넷 연결이 필요합니다. 카메라가 불가능하면 키보드형 스캐너/수동입력으로 사용할 수 있습니다. 실기 테스트는 별도 수행이 필요합니다.

서버 원본 조회는 휴대폰 번호 계정과 비밀번호로 발급된 12시간 유효 토큰을 사용합니다. 작업내역 자동 동기화는 아직 구현하지 않았으며, 사용자/센터별 권한 분리는 다센터 운영 전에 추가해야 합니다.

## 배송 지도 및 순번 편집 (2026-11-18)

- 배송시작/배송 목록 화면 **최상단**에 큰 NAVER 지도 배치. 태블릿·모바일 화면 크기에 맞춰 높이 조정.
- 지도는 선택 날짜의 **모든 회차 배송지**를 표시하고, 목록은 선택한 회차만 보여 줍니다.
- 번호 마커는 `회차 + 해당 회차 방문 순번`을 표시하며 배송 완료 여부에 따라 색상이 바뀝니다.
- 지도 마커 선택 → 해당 회차로 이동 → 배송 정보 수정. 상세 편집 지도는 기존처럼 중앙 고정 마커로 정밀 위치 보정.
- 목록에서 ↑, ↓, 순번 선택으로 방문 순서를 직접 편집. 로컬 저장 이후 지도 번호 즉시 반영.
- 저장된 좌표가 없고 주소가 있는 배송지는 지도 화면을 열 때 NAVER Geocoding으로 조회해 좌표를 로컬 저장합니다. 주소 미입력 또는 검색 실패 시 지도에 표시되지 않으며, `지도 표시 / 전체 / 위치 미확인` 건수를 확인할 수 있습니다.
- **전체 보기**로 표시된 배송지의 지도를 맞춥니다. 초기 위치가 여러 곳 조회되면 운전자가 지도를 직접 이동하기 전까지 범위를 갱신합니다.
- 경로 자동 최적화·도로별 경로선·서버 동기화는 이번 구현 범위에 포함되지 않습니다. 순번은 기사 수동 조정입니다.


## 휴대폰 번호 사용자 ID (2026-11-18)

- 최초 실행 시 본인 휴대폰 번호를 입력하면 이후 자동 선택됩니다. 초기화면의 번호 버튼으로 다시 확인하거나 변경할 수 있습니다.
- 기존 브라우저 저장 배송 목록은 볼 수 있지만 **새 운송장 스캔·등록은 서버 로그인과 원본 조회 성공이 필수**입니다. 현재 SMS 번호 소유자 검증은 없습니다.
- 이 브라우저에서는 전화번호별 localStorage 키로 배송 자료를 구분합니다. 번호를 바꾸면 해당 번호의 별도 자료가 열리고 이전 번호의 자료는 삭제되지 않습니다.
- 기존 단일 localStorage 배송 자료가 있으면 첫 전화번호 등록 때 복사해 이어서 사용하며 원본 데이터 키는 삭제하지 않습니다.
- 번호 자체가 서버 계정, 본인 인증, 공유 로그인 또는 장치 간 동기화를 제공하지는 않습니다. 실제 서버 동기화를 구현할 때는 별도의 인증과 데이터 접근 제어가 필요합니다.

## 신규 비밀번호 인증 API 준비

- 초기화면 DAILY 옆에 등록한 휴대폰 번호를 표시합니다.
- 사용자 화면에 전화번호와 비밀번호, 가입·로그인 버튼을 추가했습니다.
- `api/app.py`는 가입/로그인/세션 확인/로그아웃 API를 제공하며 서버 환경변수로 비밀키를 받습니다. 비밀번호는 scrypt 해시로 저장합니다.
- **저장소 반영만 완료**한 상태입니다. 실제 API 서버 배포, Nginx 프록시, SMS 본인확인과 배송 데이터 서버 동기화는 아직 필요합니다. 자세한 실행 조건은 `api/README.md`를 참고하세요.
- 기존 자료를 없애지 않기 위해 '기존 기기 자료만 보기' 버튼을 유지했습니다. **이 상태로는 새 송장을 스캔할 수 없습니다.**

## 카메라 자동 초점 및 13+3 운송장 조회 (2026-11-18)

- 카메라 스캔은 후면 카메라를 우선 요청하며, 브라우저·하드웨어가 `focusMode: continuous`를 지원하면 연속 자동 초점을 활성화합니다. 지원하지 않는 기기는 기본 카메라 초점 동작을 사용합니다.
- 무선 바코드 리더기 입력창은 자동 포커스하며 Android 소프트 키보드는 사용자가 직접 입력창을 누를 때만 열립니다.
- 기본 운송장 13자리 `2139602023214`, 물품 1·2의 16자리 바코드 `2139602023214001`, `2139602023214002`는 원본 조회 시 동일한 **13자리 기본 운송장**으로 조회합니다. 그러나 물품 스캔번호 `001`, `002`는 DDSM 로컬 자료의 `scannedItems`에 별도로 저장합니다.
- 같은 기본 운송장은 같은 회차에 배송지 하나로 등록하며, 서로 다른 물품번호는 해당 배송지에 누적합니다.
- 원본 조회는 선택 날짜의 관리자 업로드 데이터만 검색하므로 **엑셀 업로드 날짜와 DDSM 날짜를 일치**시켜야 합니다.
- 서버 조회가 실패하거나 배송기사가 로그인하지 않은 경우 **송장을 등록하지 않으며** 오류를 표시합니다. 스캔 시 로컬 등록으로 우회하지 않습니다.
- 서버 원본의 수취인·주소 등을 가져오지만 **DSD와 DDSM 배송완료 상태 동기화는 하지 않습니다.**

### S10 API 활성화

센터 관리자 서버가 실제 사용하는 `~/dsd/admin.py`를 [dsd/api/admin.py](../dsd/api/admin.py)로 교체해야 새 전용 엔드포인트가 등록됩니다. 기존 `dsd.py`는 그대로 두고 Waitress만 재시작하면 됩니다.

배송기사별 사전 전화번호 승인 목록은 사용하지 않습니다. 휴대폰 번호와 비밀번호로 로그인한 사용자는 해당 날짜의 **정확한 13자리 기본 운송장번호**를 입력한 경우에만 해당 원본 한 건을 조회할 수 있습니다.

- `POST /dsd/api/ddsm/login`: JSON `{"phone":"...","password":"..."}` → `access_token`.
- `GET /dsd/api/ddsm/waybill?date=YYYY-MM-DD&barcode=...`: `Authorization: Bearer ...`. 13자리 기본 번호 **정확히 일치**하는 원본 배송 건만 반환.
- `POST /dsd/api/ddsm/logout`: 토큰 폐기.
- 브라우저 요청 주소: `https://mrdindoin.ddns.net/dsd-center-api/ddsm/...`
- 메인 앱에서는 휴대폰 번호를 눌러 가입 또는 로그인합니다. 계정 가입 후 로그인이 필요합니다.
- 계정 토큰은 브라우저 메모리에서만 유지되며 새로고침 시 다시 로그인해야 합니다.

기존 DSD 배송기사 스캔 및 기존 관리자 API는 그대로 유지합니다.

## 서버 조회 의무화 (2026-11-18)

- DSD 센터 관리자 페이지의 **엑셀 업로드는 S10 서버로 POST 전송**됩니다. `dsd/api/admin.py`의 `POST /dsd/api/admin/import`가 원본을 파싱해 SQLite `admin_deliveries`와 배송지 레지스트리에 저장합니다.
- DDSM의 모든 신규 스캔(카메라, 키보드형 리더, 수동 입력)은 로그인 후 `GET /dsd/api/ddsm/waybill`을 호출해야 합니다. 조회가 성공한 경우에만 현재 회차의 로컬 작업 목록에 등록합니다. 기존 자료는 삭제하지 않습니다.
- **엑셀 원본은 브라우저 저장소에 저장하지 않습니다.** 단, 현재 DDSM의 기사별 스캔 결과와 배송완료·회차 작업 목록은 여전히 브라우저 localStorage에 저장됩니다. 이 데이터까지 S10에 저장·동기화하는 기능은 별도로 구현해야 합니다.
- 새로고침하면 보호된 로그인 토큰이 사라지므로 운송장 스캔 전 다시 로그인해야 합니다. 가입만으로 로그인된 상태는 아닙니다.
- S10에서 실행 중인 `admin.py`에 신규 `/dsd/api/ddsm/login`, `/dsd/api/ddsm/waybill` 경로가 배포되지 않았다면 서버 조회가 실패합니다. 새 서버 파일 적용과 Waitress 재시작이 필요합니다.

## 기사 계정 + 배송일 서버 동기화 (2026-11-18)

- 센터 ID로 작업을 분리하지 않습니다. S10 SQLite의 `ddsm_driver_days`에 **인증된 기사 휴대폰 번호 + 배송일**을 복합 기본키로 저장합니다.
- `GET /dsd/api/ddsm/work-day?date=YYYY-MM-DD`: 로그인 기사 자신의 당일 전체 회차·배송지·배송 완료·스캔된 물품·메모·순서를 조회합니다.
- `PUT /dsd/api/ddsm/work-day`: `{date,revision,day}` 데이터를 서버에 저장합니다. 인증된 계정만 수정할 수 있고, 버전 충돌은 HTTP 409로 차단합니다.
- 클라이언트는 로그인·날짜 변경 시 서버 자료를 불러오고, 작업 변경 시 서버로 전송하며, 화면이 활성화된 동안 약 3초 간격으로 타 기기 변경 여부를 확인합니다.
- 기존 로컬 작업이 있지만 해당 서버 날짜에 아직 기록이 없는 경우 **최초 로그인 시 1회 이전을 시도**합니다. 기존 자료를 복사 백업합니다. 서버에 이미 자료가 있다면 서버 자료를 우선시하며 기존 로컬 작업은 별도 보관합니다.
- 서버 연결 장애 시 로컬 사본을 보존하고 재시도합니다. **409 충돌은 자동 병합하지 않으며, 충돌 알림 후 수동 확인이 필요합니다.** 따라서 서로 다른 기기의 동시 작업에 대한 무충돌 병합은 지원하지 않습니다.
- 센터의 원본 운송장 엑셀 자료와 기사의 작업 데이터는 별개입니다. 서버 소스 변경만으로 실서버가 적용되지는 않으며, S10의 `~/dsd/admin.py` 교체 및 Waitress 재시작이 필요합니다.
- 운영 시 계정 등록·비밀번호 정책, 원본 접근 권한, 데이터 보존·백업 등을 점검해야 합니다.
