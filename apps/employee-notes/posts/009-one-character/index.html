ISSUE 09 / ONE CHARACTER

한 글자인데,
왜 길이는 둘이지?

웃는 얼굴 하나를 넣었다. 프로그램은 둘이라고 했다. 화면의 글자와 문자열의 칸, 저장할 바이트 사이를 따라가 본다.

  14. 컴퓨터가 세지 못한 것은 글자가 아니라 우리의 뜻이었다

별명을 한 글자만 넣었다. 웃는 얼굴 하나다. 그런데 화면 아래에는 ‘2자’라고 나온다. 다른 곳에 붙여 넣으니 이번에는 ‘4바이트’라고 한다. 컴퓨터는 이렇게 간단한 것도 못 세는 걸까. 사실 세 프로그램은 서로 다른 자를 들고 같은 대상을 재고 있다. 문제는 모두 자기 숫자를 그냥 ‘길이’라고 부른다는 데 있다.

한글도 이 이야기 밖에 있지 않다. 눈에는 똑같은 ‘가’가 보이는데 두 문자열을 비교하면 다르다고 나올 수 있다. 문자 하나를 지웠더니 이모지가 깨지거나, 입력 제한에 맞춰 붙여 넣었는데 저장 단계에서 거절되는 일도 같은 주변에서 일어난다. 화면 위의 한 덩어리와 메모리 안의 한 칸은 처음부터 같은 단위가 아니다.

이번 글은 가상의 별명 서비스 ‘이름표’에서 출발한다. 서비스와 담당자 소라, 등장하는 장애 상황은 설명을 위해 만든 사례다. 실제 서비스의 장애 기록이나 사용자 실험이 아니다. 기술 자료는 2026년 10월 4일 기준으로 확인했다. 아래 체험은 이 브라우저의 문자 API로 실제 값을 계산하지만, 특정 입력기나 모든 운영체제의 표시 모양까지 재현하지는 않는다.

01 / SCENE

이름표는 하나인데 계산기는 네 개였다

소라는 이름표에 영문 A를 넣어 본다. 프로그램의 길이는 1이다. 코드 포인트를 세어도 1, 화면의 문자 덩어리로 나누어도 1, UTF-8로 바꾼 바이트 수도 1이다. 첫 시험이 너무 잘 맞아서 담당자는 이 네 숫자가 언제나 같은 것이라고 생각한다. 다음으로 한글 ‘가’를 넣자 앞의 세 숫자는 1인데 바이트 수가 3이 된다.

이번에는 웃는 얼굴 😀를 넣는다. JavaScript 문자열의 length는 2, 코드 포인트 수는 1, 이 글의 체험에서 세는 문자 덩어리 수는 1, UTF-8 바이트 수는 4다. 어느 숫자도 그 자체로 오답은 아니다. 잘못된 것은 length가 무엇을 세는지 밝히지 않은 채 ‘사용자가 보는 글자 수’라는 이름으로 표시한 것이다.[1][2]

소라는 사용자가 닉네임을 입력하는 화면을 만들고 있다. 사용자는 저장장치의 칸 수를 보고 싶은 것이 아니다. 자신이 붙인 이름이 얼마나 긴지 알고 싶다. 반면 서버 운영자는 요청 본문이 얼마나 큰지 제한해야 할 수도 있다. 두 사람의 요구는 둘 다 정당하지만 하나의 숫자로 대신할 수는 없다.

종이에 쓴 주소를 떠올리면 편하다. 글자의 개수, 잉크로 칠한 면적, 봉투의 무게는 같은 편지에 관한 수치다. 그렇다고 글자가 열 개인 편지가 반드시 열 그램인 것은 아니다. 컴퓨터의 글자도 표현하는 층마다 다른 비용과 경계를 갖는다. 먼저 ‘무엇 하나를 하나로 세는가’를 정해야 길이라는 말에 답이 생긴다.

02 / POINTS

문자에 붙인 번호와 화면의 그림을 나눈다

Unicode는 문자 정보를 다루기 위한 공통 체계를 제공한다. 코드 포인트는 그 안에서 위치를 가리키는 번호이고 U+0041 같은 표기로 쓸 수 있다. 이 예의 번호는 라틴 대문자 A에 해당한다. 번호를 보면 글꼴이 바뀌어도 어떤 문자를 다루려는지 이야기할 수 있다. 다만 번호 하나가 반드시 눈에 보이는 독립된 글자 하나를 뜻하는 것은 아니다.[3]

어떤 코드 포인트는 앞의 글자에 붙는 결합 표시이고, 어떤 것은 표시 방식이나 결합에 관여한다. 따라서 코드 포인트 목록을 읽는 일과 완성된 화면을 읽는 일은 다르다. 사람은 결과를 한 덩어리로 보지만 프로그램은 그 결과를 만드는 여러 요소를 순서대로 보관할 수 있다. 문자라는 단어 안에 이미 여러 층이 들어 있다.

글꼴은 또 다른 층이다. 같은 텍스트라도 글꼴이 바뀌면 굵기와 모양이 달라진다. 두 글자를 붙여 그린 모양이 생겼다고 저장된 코드 포인트 수가 저절로 줄지는 않는다. 반대로 하나의 문자 덩어리가 글꼴의 지원 부족 때문에 여러 조각으로 보일 수도 있다. 화면을 확대해 몇 덩어리인지 세는 일로 내부 표현을 확정할 수 없는 이유다.

이름표의 담당자가 스크린샷만 보고 오류를 조사하면 여기서 막힌다. A라는 모양이 보인다는 사실은 확인했지만 어떤 번호가 들어왔는지는 아직 모른다. 문자 문제를 조사할 때 원문과 함께 코드 포인트를 펼쳐 보는 습관이 유용하다. 겉모양을 버리라는 뜻이 아니라, 같은 대상을 다른 층에서도 확인하자는 뜻이다.

03 / UNITS

JavaScript의 length는 UTF-16 칸을 센다

JavaScript의 문자열은 16비트 코드 단위의 연속으로 정의된다. 문자열의 length는 그 코드 단위 개수다. 많은 익숙한 문자는 한 코드 단위로 표현되지만, 기본 다국어 평면 밖의 문자를 UTF-16으로 표현할 때는 두 코드 단위를 사용한다. 웃는 얼굴 😀가 length 2인 이유가 여기에 있다.[2][4]

이 두 단위를 서로게이트 쌍이라고 부른다. 중요한 것은 어려운 이름보다 ‘둘이 한 코드 포인트를 표현한다’는 관계다. 책상 위에 놓인 상자 두 개가 한 세트 제품을 담고 있다고 생각해 보자. 상자 수를 묻는 창고 직원에게 2는 맞는 답이다. 세트 수를 묻는 고객에게도 2라고 답하면 의미가 틀어진다.

그래서 문자열의 첫 칸을 가져오는 코드가 사람이 기대한 첫 글자를 언제나 가져오는 것은 아니다. 😀의 첫 코드 단위만 잘라내면 완전한 코드 포인트가 남지 않는다. 이렇게 떨어진 서로게이트는 이후 처리 과정에서 대체 문자로 표시되거나 다른 방식으로 다루어질 수 있다. 앞에서부터 몇 칸을 잘랐는지와 정상적인 문자가 남았는지를 구분해야 한다.[4]

그렇다고 JavaScript가 모든 문자열을 실제 메모리에서 무조건 정확히 두 바이트씩 저장한다고 추론해서도 안 된다. 언어가 관찰 가능한 문자열을 어떤 단위로 정의하는지와 엔진 내부 최적화는 별개다. 여기서 확인하는 것은 프로그램이 length와 인덱스로 보게 되는 약속이다. 메모리 사용량 전체를 계산하는 도구로 length를 가져다 쓰는 것은 다른 질문을 섞는 일이다.

04 / CLUSTERS

코드 포인트를 세어도 한 글자가 남는다

문자열을 펼침 문법이나 문자열 반복자로 순회하면 서로게이트 쌍을 하나의 코드 포인트로 다룰 수 있다.[1] 그래서 Array.from으로 만든 배열의 길이는 😀에 대해 1이다. 이름표의 담당자는 안심하고 코드를 바꾼다. 그런데 다음 사용자가 피부색이 붙은 손 모양이나 가족 이모지를 넣자 숫자가 다시 기대와 달라진다.

여러 코드 포인트가 하나의 문자 덩어리로 느껴지는 경우가 있기 때문이다. Unicode의 텍스트 분할 규칙은 이런 사용자 인식에 가까운 단위를 다루기 위해 확장 자소 군집, 즉 extended grapheme cluster의 경계를 정의한다. 한 코드 포인트를 한 항목으로 세는 것보다 텍스트 편집에 더 알맞은 경계를 얻을 수 있다.[3]

‘사람이 보는 글자’라는 설명도 완전한 정의는 아니다. 언어와 상황에 따라 사람이 생각하는 경계가 달라질 수 있고, 표준의 기본 분할 규칙이 모든 인식을 똑같이 대변하지는 않는다. 이 글에서는 편의를 위해 ‘문자 덩어리’라고 부르되, 체험의 숫자는 Intl.Segmenter의 grapheme 분할 결과라고 명확히 적는다.

이름표의 핵심 질문도 달라진다. ‘정답인 글자 수 함수를 찾아라’에서 ‘이 제품이 약속할 문자 단위를 정하라’로 바뀐다. 저장 비용을 제한할 때, 말줄임표를 붙일 때, 사용자의 이름 길이를 안내할 때 서로 다른 단위가 필요할 수 있다. 한 함수로 모든 문제를 해결하려고 하면 다른 곳에서 다시 오해가 생긴다.

05 / EMOJI

가족 한 팀 뒤에 여러 사람이 서 있다

가족 이모지 👨‍👩‍👧‍👦를 코드 포인트로 펼치면 사람을 나타내는 문자들과 그 사이의 ZWJ가 보인다. ZWJ는 폭이 없는 결합 문자로, 이모지 시퀀스의 연결에 쓰인다. 지원하는 환경에서는 이 시퀀스가 한 가족 모습으로 표시될 수 있다. Unicode Emoji 문서는 이런 시퀀스와 표현 선택자의 구조를 설명한다.[5]

이 예는 코드 포인트 일곱 개, UTF-16 코드 단위 열한 개, UTF-8 스물다섯 바이트다. 이 글의 체험에서 지원되는 분할기로는 문자 덩어리 하나로 계산된다. 숫자가 커 보인다고 사진 파일 일곱 장이 숨어 있는 것은 아니다. 저장된 것은 그림 자체가 아니라 문자 시퀀스이며, 표시 환경이 그것을 그린다.

같은 시퀀스를 오래된 환경에서 열었을 때 여러 사람으로 떨어져 보인다고 해서 반드시 파일 내용이 변한 것은 아니다. 표시 지원의 차이일 수 있다. 반대로 비슷한 그림이 보인다는 이유로 내부 시퀀스가 같다고 단정할 수도 없다. 외형과 데이터는 서로 영향을 주지만 일대일로 붙어 있는 관계는 아니다.[5]

소라는 이제 이름표의 남은 글자 수만 고치는 데서 멈추지 않는다. 사용자에게 보이는 미리보기와 잘라내는 위치도 같은 기준인지 살펴본다. 입력 단계에서는 가족을 하나로 세어 통과시켰는데 저장 전에 코드 단위 열 개로 잘라버린다면, 마지막 가족 구성원이나 연결 정보가 끊어질 수 있다. 센 기준과 자른 기준이 달라지면 친절한 안내가 소용없어진다.

06 / HANGUL

같은 ‘가’를 서로 다른 순서로 적을 수 있다

한글 ‘가’도 흥미로운 예다. 완성된 음절 U+AC00 하나로 나타낼 수 있고, 초성 U+1100과 중성 U+1161의 조합으로 나타낼 수도 있다. 이 둘은 Unicode에서 정준적으로 동등한 표현 관계를 가진다. 눈에는 비슷하게 보이더라도 원래 코드 포인트의 배열은 하나와 둘로 다르다.[6]

여기서 말하는 초성과 중성은 키보드에서 따로 적은 호환 자모 ‘ㄱ’과 ‘ㅏ’를 무조건 이어 붙인 것과 같지 않다. 코드 포인트가 다르기 때문이다. 이 글의 ‘분해 한글’ 예시는 정확히 U+1100과 U+1161을 사용한다. 작은 차이를 생략하면 독자가 직접 따라 했을 때 다른 결과를 보고 더 혼란스러워질 수 있다.

이름표에 ‘가’를 저장한 사람과 다른 곳에서 복사한 ‘가’를 붙여 넣은 사람을 생각해 보자. 서비스가 코드 단위 배열만 그대로 비교하면 같아 보이는 두 이름을 다르다고 판단할 수 있다. 검색에도 영향을 줄 수 있다. 하지만 실제 파일시스템이나 검색 제품이 모두 같은 비교 규칙을 쓴다고 일반화할 수는 없다. 이 사례는 문자열 그대로의 비교에서 출발한다.

문제의 본질은 화면이 거짓말한다는 데 있지 않다. 화면은 문자들을 그리는 일을 했고 비교 연산은 저장된 순서를 비교했다. 둘은 각자의 계약대로 일했다. 제품이 두 계약 사이를 연결하지 않았을 뿐이다. 그래서 사용자가 ‘분명 같은 글자인데요’라고 말할 때 프로그램의 비교 결과만 들이밀어서는 설명이 끝나지 않는다.

07 / NORMALIZE

정규화는 같은 표현을 비교할 기준을 고르는 일

정규화는 이런 표현 차이를 일정한 형식으로 다루는 방법이다. NFC는 정준 분해 뒤 가능한 결합을 수행하는 형식이고, NFD는 정준 분해 형태다. 한글 예에서는 분해된 초성·중성 시퀀스를 NFC로 바꾸면 완성 음절 ‘가’와 같은 표현이 된다. JavaScript에서는 normalize에 형식을 지정해 결과 문자열을 얻는다.[6][7]

변환은 원본 문자열을 제자리에서 바꾸는 동작이 아니다. 결과를 별도로 얻는다. 이 글의 체험도 입력한 내용을 자동으로 교체하지 않고 원문과 NFC 결과를 나란히 표시한다. 독자가 차이를 관찰하는 도구에서 원문을 몰래 고쳐 버리면, 무엇 때문에 숫자가 달랐는지 확인할 근거가 사라지기 때문이다.

정규화가 모든 닮은꼴을 같은 문자로 만드는 마법은 아니다. NFC를 적용해도 라틴 대문자 A와 키릴 문자 А는 같은 문자열이 되지 않는다. 두 문자가 특정 글꼴에서 닮아 보이는 문제와 정준적으로 같은 문자의 표현 차이는 다른 문제다. Unicode는 혼동 가능한 식별자 문제를 별도 보안 문서에서 다룬다.[8]

정규화 형식에도 목적 차이가 있다. NFKC와 NFKD는 호환성 차이까지 다루므로 정보의 일부 구분을 없앨 수 있다. 예를 들어 원문 보존이 중요한 기록에 제품의 검색 편의를 위한 변환을 무조건 적용하면 작성자의 표현이 달라질 수 있다.[6] 이름표의 검색 키를 만드는 일과 사용자가 쓴 원문을 보관하는 일을 나누어 설계할 이유다.

08 / BYTES

바이트 수는 글자를 담아 옮기는 비용이다

UTF-8 바이트 수는 다른 방향의 질문이다. 문자를 어떤 바이트 열로 인코딩했을 때 길이가 얼마인가를 묻는다. 브라우저의 TextEncoder는 JavaScript 문자열을 UTF-8 바이트 배열로 바꾼다. 그 배열의 길이를 확인하면 문자열 내용 자체의 UTF-8 바이트 수를 얻을 수 있다.[9] 네트워크 요청 전체 크기와는 아직 다르다.

예를 들어 이 글의 ‘가’는 UTF-8 세 바이트, 😀는 네 바이트다. 분해 한글의 초성과 중성을 각각 담으면 여섯 바이트가 된다. NFC 결과는 같은 한 음절로 결합되어 세 바이트가 된다. 문자 덩어리 수는 하나로 같아도 전송되는 바이트 열은 달라질 수 있다. 눈에 보이는 길이와 저장 단위가 분리되는 장면이다.

여기에 JSON의 속성 이름과 따옴표가 붙으면 전송 본문은 더 커진다. HTTP 헤더나 압축, 다른 포장까지 포함한 전체 통신량도 별도의 수치다. TextEncoder로 별명만 재어 놓고 ‘이 요청은 정확히 몇 바이트를 사용한다’고 말하면 범위를 과장하게 된다. 측정 결과에는 어떤 대상만 셌는지 이름표가 붙어야 한다.

바이트 제한이 필요 없다는 뜻은 아니다. 사용자에게 문자 덩어리 수로 친절하게 안내하더라도 저장소와 통신에는 별도의 크기 한도가 필요할 수 있다. 이때 사용자에게 서로 다른 제한을 설명해야 한다. ‘이름이 길다’는 한 문장으로 숨기면 사람은 더 짧아 보이는 이모지를 넣고도 계속 거절되는 상황을 이해할 수 없다.

09 / LIMIT

열 글자 제한이라는 약속부터 정확히 쓴다

이름표의 기획서에는 ‘별명은 열 글자까지’라고 적혀 있었다. 처음에는 충분히 명확한 요구처럼 보였다. 이제 소라는 되묻는다. 열 코드 단위인가, 열 코드 포인트인가, 열 문자 덩어리인가. 공백은 포함하는가. 정규화 전과 후 중 어느 쪽인가. 질문이 늘어난 것은 일을 어렵게 만들기 위해서가 아니라, 이미 숨어 있던 선택을 드러내기 위해서다.

HTML의 maxlength는 UTF-16 코드 단위를 기준으로 길이를 제한한다.[10] 따라서 maxlength를 10으로 둔 것만으로 모든 사용자에게 ‘보이는 글자 열 개’를 허용했다고 말할 수 없다. HTML 속성이 제공하는 기능과 제품이 약속한 경험을 구분해야 한다. 기본 동작을 그대로 선택하는 것도 선택이지만, 그 뜻을 알고 해야 한다.

소라는 이름표의 정책을 ‘확장 자소 군집 기준 열 개, 공백 포함’으로 정했다고 가정한다. 그렇다면 안내 숫자와 제출 검사, 서버의 대응 규칙이 그 약속을 따라야 한다. 저장소에는 추가 바이트 제한이 있다면 함께 밝혀야 한다. 앞단에서 통과한 입력이 뒤에서 이유 없이 거절되는 일을 줄이려면 층마다 쓰는 기준을 맞춰볼 필요가 있다.

더 긴 결합 시퀀스가 하나의 문자 덩어리를 이룰 수도 있으므로 덩어리 수 제한만으로 처리할 데이터의 크기를 충분히 제한했다고 단정하지 않는다. 사람에게 의미 있는 길이와 자원 사용량의 상한을 각각 다루는 것이 낫다. 이것은 같은 일을 두 번 검사하는 것이 아니라, 서로 다른 문제를 두 개의 단위로 검사하는 것이다.

10 / CUT

세는 기준과 자르는 기준을 맞춘다

화면 카드에 이름 앞부분만 보여주고 말줄임표를 붙인다고 하자. 담당자는 먼저 코드 단위 열 개를 자르는 방법을 떠올린다. 이 방식은 서로게이트 쌍 중간을 가를 수 있다. 그 문제를 피해 코드 포인트 단위로 자르더라도 결합 문자나 이모지 시퀀스 중간에서 끊길 가능성은 남는다. 자르는 대상의 경계가 다르기 때문이다.

Intl.Segmenter는 지정한 세분성에 따라 문자열을 나누는 인터페이스다. grapheme으로 나눈 결과를 이용하면 이번 글에서 정한 문자 덩어리의 경계에서 앞부분을 선택할 수 있다.[11] 그러나 이것이 카드 폭을 자동으로 맞춰준다는 뜻은 아니다. 같은 덩어리 열 개라도 실제 표시 폭은 글꼴과 내용에 따라 달라질 수 있다.

이름표에서는 원문 자체를 줄이는 일과 화면에서만 짧게 보이는 일을 나눌 수 있다. 목록 카드에는 공간에 맞춰 일부만 보여주되 상세 화면에서는 전체 이름을 제공하는 것이다. 저장할 때 이름을 잘라 없애면 나중에 창이 넓어져도 복구할 수 없다. 표시 편의를 위해 데이터를 파괴할 필요가 있는지 먼저 물어야 한다.

삭제 키의 동작도 특정 입력기와 편집기의 규칙이 관여하므로 이 글의 분할기 결과만으로 모든 환경을 단정하지 않는다. 체험에서는 경계를 보여주는 데 집중한다. 하나의 경계 알고리즘을 관찰한 결과를 모든 텍스트 편집 동작의 보증으로 확대하지 않는 것 역시 정확한 설명의 일부다.

세는 기준과 자르는 기준이 다르면
친절한 안내 뒤에서 글자가 끊어진다.

11 / COMPOSING

한글은 입력하는 도중에도 만들어지고 있다

완성된 문자열을 세는 문제와 입력 중인 문자를 다루는 문제도 구분해야 한다. 한글 입력기는 키를 누를 때마다 최종 음절을 즉시 확정하는 대신 조합 과정을 거칠 수 있다. 그 중간에 프로그램이 길이를 줄이거나 값을 교체하면 사용자가 아직 만들고 있는 글자와 충돌할 수 있다. 실제 동작은 입력기와 브라우저에 따라 시험해야 한다.

웹의 InputEvent.isComposing은 이벤트가 compositionstart 뒤, compositionend 앞의 조합 구간에서 발생했는지를 알려준다.[12] 이 신호는 완성되지 않은 입력을 무조건 최종 제출값처럼 다루지 않기 위한 단서다. 모든 입력 오류를 해결하는 스위치는 아니며 붙여 넣기와 삭제, 조합 종료 같은 경로를 함께 살펴야 한다.

이번 체험은 조합 중이라고 표시된 입력에서는 결과 갱신을 잠시 보류하고, 조합이 끝난 뒤 전체 값을 다시 계산한다. 입력창의 텍스트 자체를 자르거나 NFC로 강제 교체하지 않는다. 읽고 세는 체험이 입력 과정에 덜 끼어들도록 한 선택이다. 실제 한글 키보드의 모든 조합을 시험했다는 뜻은 아니다.

소라는 이제 ‘한글을 넣었더니 이상해졌다’는 제보를 더 구체적으로 받는다. 입력 중에 바뀌었는가, 붙여 넣은 직후인가, 저장하고 다시 열었을 때인가. 완성된 데이터가 다른지, 조합 이벤트 처리에서 끊겼는지 구분하면 수정할 위치도 달라진다. 같은 글자 문제처럼 보이지만 발생한 단계는 서로 다를 수 있다.

12 / LAB-GUIDE

같은 텍스트를 네 개의 자로 재어 보자

아래 체험에서 먼저 영문 A를 선택한다. 네 숫자가 모두 1인지 확인한다. 그다음 웃는 얼굴을 선택하면 코드 단위 2, 코드 포인트 1, 문자 덩어리 1, UTF-8 바이트 4가 된다. 이것은 서버를 호출하는 모형이 아니라 현재 실행 환경의 문자열·분할·인코딩 API로 계산한 값이다. 입력 예시의 실제 코드 포인트도 함께 표시한다.

‘분해 한글’을 선택하면 원문 코드 포인트는 U+1100, U+1161로 보인다. NFC 결과는 ‘가’이고 코드 포인트는 U+AC00이다. 원문과 NFC 결과가 같은 코드 단위 배열인지는 거짓으로 표시된다. 그러나 두 쪽을 모두 NFC로 맞춘 뒤 비교한다는 규칙을 쓰면 이 예의 표현 차이는 사라진다. 결과가 바뀐 이유는 원문이 틀려서가 아니라 비교의 기준을 정했기 때문이다.

가족 이모지 예시는 덩어리 하나 뒤의 코드 포인트 목록이 길어지는 것을 보여준다. 직접 입력할 때는 가벼운 예문을 사용하자. 이 체험 코드는 값을 서버로 보내거나 브라우저 저장소에 기록하지 않는다. 다만 페이지에는 기존 광고 스크립트가 있으므로 비밀번호나 민감한 원문을 시험 재료로 쓰는 기능으로 설계하지 않았다.

빈 입력은 네 숫자를 모두 0으로 표시하고 아직 텍스트가 없다고 안내한다. 분할 기능이 없는 환경에서는 문자 덩어리 수를 코드 포인트 수로 몰래 대신하지 않고 지원되지 않는다고 표시한다. 대용량 붙여 넣기로 화면이 멈추는 일을 줄이기 위해 분석 범위도 제한한다. 실패를 숨기지 않는 안내가 네 숫자를 설명하는 것만큼 중요하다.

13 / POLICY

같다고 판단하기 전에 무엇을 보존할지 정한다

정규화와 분할을 알게 되면 모든 문자열을 한 번에 정리하고 싶어진다. 하지만 이름표의 표시용 이름, 검색용 키, 비밀번호, 원문 기록은 같은 목적의 데이터가 아니다. 보기 편하게 만들기 위한 변환이 다른 곳에서는 의도하지 않은 변경이 될 수 있다. 이 글의 체험이 원문과 결과를 나란히 남기는 이유도 그 차이를 보여주기 위해서다.

예를 들어 두 이름을 같은 계정 이름으로 취급하기로 했다면, 그 정책에 따라 이미 등록된 이름들이 충돌하지 않는지도 고려해야 한다. 표시용 텍스트를 바꾸는 것과 계정을 식별하는 키를 바꾸는 것은 영향이 다르다. ‘정규화하면 좋다’는 일반론만으로 기존 서비스의 저장된 이름을 일괄 교체할 수 없는 이유다.

글자 수를 로그에 기록할 때도 단위와 처리 순서를 남기면 도움이 된다. 원문 코드 단위 수와 NFC 뒤 바이트 수를 서로 비교해놓고 수치가 이상하다고 판단해서는 안 된다. 무엇을 어떤 순서로 변환했는지, 어떤 단위를 셌는지가 같아야 두 결과를 비교할 수 있다. 숫자만 저장하면 사람이 나중에 숨은 정의를 추측해야 한다.

여러 장치에서 최신 이모지나 분할 결과를 비교할 때는 사용한 환경의 지원 수준도 생각한다. 표준의 개정과 브라우저의 구현은 항상 같은 날 움직이지 않는다. 이 글의 예시 값이 나오는지 직접 확인할 수 있게 한 까닭이다. 문서에 적힌 원리와 내 기기에서 관찰한 결과를 연결하되, 둘이 같다고 미리 가정하지 않는다.

14 / ENDING

컴퓨터가 세지 못한 것은 글자가 아니라 우리의 뜻이었다

처음의 웃는 얼굴로 돌아가 보자. 사람은 하나를 넣었고 JavaScript는 둘을 셌다. 바이트 인코더는 넷을 셌다. 이 장면에서 가장 먼저 고쳐야 할 것은 덧셈이 아니다. 서로 다른 단위에 같은 ‘글자 수’라는 이름표를 붙인 설명이다. 단위를 밝히면 모순처럼 보이던 숫자들이 한 텍스트의 서로 다른 모습이 된다.

코드 포인트는 어떤 요소들이 들어 있는지 살피게 해준다. 코드 단위는 언어의 문자열 연산이 어디를 기준으로 움직이는지 보여준다. 자소 군집은 사용자가 인식하는 덩어리에 가까운 경계를 제공한다. 바이트 수는 정해진 인코딩으로 표현한 크기를 알려준다. 어느 한 층만 진짜이고 나머지가 가짜인 것이 아니다.

다음에 ‘열 글자까지만’이라는 요구를 보게 되면 단위를 물어보자. 같은 모양인데 검색이 안 되면 원문의 번호와 정규화 기준을 살펴보자. 이모지가 잘렸다면 무엇을 하나로 보고 잘랐는지 확인하자. 복잡한 Unicode 표 전체를 외우지 않아도 질문의 층을 구분하는 것만으로 많은 오해가 줄어든다.

사람의 말은 컴퓨터 안에서 번호와 순서와 바이트가 된다. 좋은 프로그램은 그 변환을 사용자에게 떠넘기지 않으면서도 내부에서는 정확히 구분한다. 화면에는 한 글자가 놓여 있다. 그 한 글자를 온전히 지키려면, 화면 뒤에서는 하나라는 말의 뜻을 여러 번 물어야 한다.
