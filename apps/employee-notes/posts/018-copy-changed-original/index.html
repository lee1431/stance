ISSUE 18 / COPYING RELATIONSHIPS

복사했는데,
왜 원본도 바뀌었지?

복사 버튼을 눌렀다고 언제나 새 세계가 생기는 것은 아니다. 어떤 복사는 이름만 하나 더 만들고, 어떤 복사는 바깥 상자만 새로 만들며, 어떤 복사는 연결된 객체 그래프 전체를 다시 그린다.

가상의 쇼핑몰 ‘겹상자’에서 운영자가 상품 하나를 복사해 행사판을 만들었다. 행사판의 배송지를 원주로 바꿨는데 잠시 뒤 원본 상품의 배송지도 원주로 변해 있었다. 화면에는 분명 ‘복사’처럼 보이는 두 카드가 있었고 저장 버튼도 따로였다. 그런데 프로그램 안에서는 두 이름이 같은 중첩 객체 하나를 바라보고 있었다.

이런 버그는 컴퓨터가 원본과 복사본을 몰라서 생기지 않는다. 개발자가 어떤 관계를 만들었는지 컴퓨터가 아주 정확히 지켰기 때문에 생긴다. copy = original은 객체를 하나 더 만들어 달라는 문장이 아니라, original이 가진 값을 copy에도 넣으라는 문장이다. 그 값이 객체를 가리키는 값이라면 두 변수의 목적지는 같아진다.

문제는 ‘값’, ‘참조’, ‘복사’가 일상어와 프로그래밍 언어에서 조금씩 다른 뜻으로 쓰인다는 데 있다. 종이를 복사하면 독립된 두 장이 생긴다. 파일을 복사하면 대체로 별도 파일이 생긴다. 하지만 객체 대입은 새 상자를 만들지 않을 수 있고, 전개 구문은 겉상자만 만들며, 구조화 복제는 지원되는 객체 그래프를 새로 구성한다. 전송은 아예 소유권을 넘겨 원본 쪽 사용을 끝낸다.

이 글은 브라우저의 JavaScript를 중심으로 설명한다. 주소나 메모리 배치의 세부 구현을 가르치는 글이 아니라, 관찰 가능한 객체 동일성과 복사 규칙을 다룬다. 겹상자와 상품 자료는 설명을 위한 가상 사례이며 실제 장애 보고나 성능 측정이 아니다. 기술 내용은 2026년 10월 5일 기준 ECMAScript와 WHATWG 표준, MDN 문서를 확인했다.

01 / TWO CARDS, ONE NESTED OBJECT

분명 복사본만 고쳤는데

겹상자의 상품 자료를 단순하게 줄여 보자. 바깥 객체에는 상품명과 가격이 있고, shipping 속성에는 도시와 창고를 담은 또 다른 객체가 있다. 운영 화면은 이 자료를 읽어 원본 카드와 행사판 카드를 그렸다. 두 카드가 보인다는 사실은 객체가 두 개라는 증거가 아니다. 같은 객체를 두 번 그려도 화면에는 두 카드가 생긴다.

개발자는 const eventItem = originalItem을 쓰고 행사판 이름만 새로 붙였다고 생각했다. 그러나 이 대입은 원본 객체를 복제하지 않는다. 두 변수에 같은 객체 값이 들어간다. 이어서 eventItem.shipping.city = '원주'를 실행하면 행사판의 별도 배송지를 고친 것이 아니라 두 변수가 함께 가리키는 shipping 객체의 속성을 고친다.

화면 프레임워크가 다시 렌더링되면 원본 카드도 바뀐 도시를 보여 준다. 사용자는 ‘복사했는데 원본이 변했다’고 말하지만, 런타임 입장에서는 원본과 복사본이라는 두 객체가 애초에 없었다. 하나의 객체 그래프에 두 진입점이 있었을 뿐이다. 버그의 핵심은 값이 잘못 전달된 것이 아니라 소유권과 공유 관계를 잘못 상상한 데 있다.

이 현상은 JavaScript만의 기묘함이 아니다. 객체나 컬렉션을 참조로 다루는 여러 언어에서 비슷한 문제가 생긴다. 다만 구체적인 문법, 값의 종류, 복사 생성자와 소유권 규칙은 언어마다 다르다. 여기서는 ‘JavaScript 객체를 다른 변수에 대입하면 같은 객체가 관찰된다’는 범위에 집중한다.

02 / WHAT EXACTLY MOVES

값을 복사한다는 말의 함정

ECMAScript는 언어 값을 Undefined, Null, Boolean, String, Symbol, Number, BigInt와 Object 같은 종류로 구분한다.[1] 변수 대입에서는 오른쪽 표현식의 값을 구해 왼쪽 바인딩에 저장한다. 숫자 7을 다른 변수에 대입하면 두 변수는 각각 7이라는 원시 값을 가진다. 한쪽을 8로 다시 대입해도 다른 쪽의 7은 변하지 않는다.

문자열도 비슷하다. 문자열 값은 불변이며, b = a 뒤에 b = b + '!'를 실행하는 것은 기존 문자열 상자를 고치는 일이 아니라 새 문자열 값을 계산해 b를 다시 묶는 일이다. 그래서 숫자와 문자열 경험만으로 객체를 예상하면 ‘대입했으니 완전히 독립된 값’이라고 오해하기 쉽다.

객체에서는 속성을 바꿀 수 있다. 두 변수에 같은 객체 값이 들어 있다면 어느 변수를 통하든 동일한 속성 집합을 관찰하고 수정할 수 있다. 여기서 참조라는 말은 객체로 가는 관찰 가능한 연결을 설명하는 유용한 모형이다. 그러나 JavaScript 코드가 언제나 실제 메모리 주소 숫자를 들고 있다는 뜻으로 확대하면 안 된다. 엔진은 객체를 옮기고 압축하며 내부 표현을 바꿀 수 있다.

중요한 구분은 ‘변수를 새 값에 다시 대입하는 일’과 ‘변수가 가리키는 객체의 속성을 바꾸는 일’이다. copy = {}는 copy의 화살표를 새 객체로 옮긴다. copy.city = '원주'는 화살표는 그대로 둔 채 목적지 객체를 바꾼다. 원본까지 변하는 버그는 대개 이 두 동작을 머릿속에서 섞을 때 시작한다.

03 / NAMES ARE NOT BOXES

변수는 객체의 별명이 될 수 있다

변수를 늘 각각의 상자로 그리면 객체 대입을 이해하기 어렵다. 객체 바깥에 변수 이름표를 두고, 이름표에서 객체로 화살표를 그려 보자. original과 copy의 화살표가 같은 객체 A에 닿으면 두 변수는 A의 별명처럼 동작한다. 어느 쪽으로 shipping.city를 읽어도 A 안의 같은 중첩 객체 B를 지나간다.

객체 A 안의 속성도 값이다. name에는 문자열 값이 들어 있고, shipping에는 객체 B를 가리키는 값이 들어 있다. 객체 그래프라는 표현은 이 중첩을 잘 보여 준다. A라는 노드에서 B라는 노드로 shipping 간선이 이어지고, B에서 도시 문자열로 간선이 이어진다.

그래프는 트리보다 현실적이다. 두 객체가 같은 하위 객체를 공유할 수 있고, 객체가 자기 자신을 가리키는 순환도 만들 수 있다. 예를 들어 조직의 여러 상품이 하나의 공용 창고 객체를 가리킬 수 있다. 이때 창고 주소를 고치면 연결된 모든 상품에서 새 주소가 보이는 것이 의도일 수도 있다. 공유는 버그가 아니라 강력한 표현 수단이다.

문제는 공유 여부가 코드의 의도와 다를 때다. 독립적인 행사판을 원했는데 공용 배송 객체를 공유했거나, 공용 설정을 원했는데 매번 깊은 복사를 만들어 서로 어긋날 수 있다. ‘참조는 나쁘고 복사는 좋다’가 아니라 어느 노드를 공유하고 어느 노드를 분리해야 하는지 결정하는 일이 설계다.

04 / SAME CONTENT IS NOT SAME IDENTITY

같은 내용과 같은 객체는 다르다

{ city: '충주' } === { city: '충주' }는 거짓이다. 두 객체의 속성과 문자열이 같아 보여도 객체 리터럴을 평가할 때 서로 다른 객체가 만들어졌기 때문이다. 반대로 const b = a; a === b는 참이다. 엄격한 동등 비교는 객체의 모든 속성을 재귀적으로 비교하는 검사가 아니라 같은 객체 값인지 확인한다.[2]

이 차이를 객체 동일성이라고 부른다. 출입증 두 장에 같은 이름이 적혀 있다고 같은 출입증은 아니다. 하나의 출입증을 두 사람이 번갈아 들고 있다면 이름은 둘이어도 물건은 하나다. 객체 비교에서 내용과 정체성을 나누면 캐시 키, 집합의 구성원, UI 변경 감지와 메모이제이션의 동작도 이해하기 쉬워진다.

깊은 복제를 하면 원본과 복제본의 내용이 처음에는 같아 보일 수 있지만 original === clone은 거짓이다. 중첩 객체도 새로 만들어졌다면 original.shipping === clone.shipping 역시 거짓이다. 반대로 얕은 복사는 바깥 객체 비교는 거짓이지만 중첩 객체 비교는 참일 수 있다. 한 문장 안에 두 종류의 관계가 공존한다.

‘같은가’를 검사할 때 먼저 무엇을 묻는지 정해야 한다. 같은 객체인지, 같은 자체 속성을 가졌는지, 도메인에서 같은 상품 ID인지, 화면에 같은 내용으로 보이는지를 구분한다. 이 질문을 생략하면 개발자는 깊은 비교를 넣어야 할 곳에 ===를 쓰거나, 동일성만 필요할 때 비싼 재귀 비교를 수행한다.

05 / ASSIGNMENT DOES NOT CLONE

대입은 복제 명령이 아니다

대입 표현식은 오른쪽 값을 얻고 왼쪽 참조가 가리키는 저장 위치에 그 값을 둔다.[3] 그 과정에는 ‘객체이면 내부를 순회해 새 객체를 만든다’는 단계가 없다. 따라서 단순 대입은 객체의 크기와 중첩 깊이에 비례하는 복사 작업을 하지 않는다. 큰 객체를 다른 변수 이름으로 다룬다고 갑자기 모든 자료를 복제하지 않는 이유다.

대입이 가볍다는 성질은 중요하다. 함수에 객체를 넘길 때마다 전체 그래프가 자동 복제된다면 비용이 예측하기 어렵고, 함수가 같은 공유 상태를 다루기도 힘들다. 대신 언어는 같은 객체 값을 전달하고, 필요한 경우 개발자가 명시적으로 새 객체를 만들도록 한다. 편리함의 반대편에는 별칭을 추적해야 하는 책임이 있다.

const도 객체를 얼리지 않는다. const item = { price: 1000 }에서 item = 다른객체처럼 바인딩을 다시 대입할 수 없을 뿐, item.price = 1200처럼 객체 속성은 바뀔 수 있다. 바인딩의 고정과 객체의 불변성을 같은 것으로 생각하면 원본 변경을 막았다고 착각한다.

Object.freeze()는 대상 객체의 자체 속성 추가·삭제·재할당을 막지만 기본적으로 얕다. 중첩 객체까지 자동으로 모두 얼리는 명령은 아니다. 그리고 동결은 복사가 아니라 변경 정책이다. 원본을 동결하고 공유할지, 필요한 가지를 복사할지, 완전히 독립된 그래프를 만들지는 별도의 선택이다.

06 / CROSSING A FUNCTION BOUNDARY

함수 경계도 연결을 끊지 않는다

함수 인자에 객체를 넣으면 매개변수는 전달된 객체 값을 받는다. 함수 안에서 매개변수 자체를 새 객체로 다시 대입해도 호출자의 변수는 바뀌지 않는다. 하지만 매개변수로 도달한 객체의 속성을 수정하면 호출자도 같은 객체에서 변경을 관찰한다. 이 둘 때문에 ‘참조로 전달된다’와 ‘값으로 전달된다’라는 짧은 구호가 자주 논쟁을 만든다.

관찰 가능한 규칙만 보자. function rename(x){ x.name='행사품' }은 공유 객체의 속성을 바꾼다. function replace(x){ x={name:'새상품'} }은 함수 안의 매개변수 바인딩만 다른 객체로 옮긴다. 호출자의 변수 화살표는 그대로다. 함수가 변수 자체를 원격 조종하는 것이 아니라, 같은 객체 값을 받아 그 객체에 접근할 수 있는 것이다.

API 설계에서는 함수가 입력을 변경하는지 계약으로 드러내야 한다. sort()처럼 배열 자체를 바꾸는 함수와 새 배열을 반환하는 함수는 호출자의 기대가 다르다. 이름, 문서, 타입과 테스트로 변경 여부를 분명히 하면 예상하지 못한 공유 상태 버그가 줄어든다.

비동기 작업에서는 더 조심해야 한다. 타이머를 등록한 뒤 실행될 때까지 같은 객체가 다른 코드에서 바뀔 수 있다. 콜백이 캡처한 것은 과거 화면의 사진이 아니라 여전히 같은 객체로 가는 연결일 수 있다. 특정 시점의 스냅샷이 필요하다면 어느 깊이까지 복사할지 명시해야 한다.

이름이 둘이라고 세계가 둘은 아니다.
화살표 끝이 같다면 변화도 함께 보인다.

07 / A NEW OUTER SHELL

얕은 복사는 한 층만 새롭다

const copy = { ...original }은 새 바깥 객체를 만든다. ECMAScript의 CopyDataProperties는 원본의 자체 속성 키를 돌며 열거 가능한 속성의 값을 읽어 대상에 데이터 속성으로 만든다.[4] 여기서 ‘속성의 값’을 복사한다는 말이 핵심이다. 그 값이 중첩 객체라면 새 중첩 객체를 자동으로 만들지 않는다.

따라서 copy.name = '행사 상품'은 원본 이름에 영향을 주지 않는다. 바깥 객체가 서로 다르고 name은 문자열 값이기 때문이다. 하지만 copy.shipping.city = '원주'는 원본에도 보인다. 두 바깥 객체의 shipping 속성이 같은 객체 B 값을 갖고 있기 때문이다. MDN은 전개 구문, Object.assign(), 배열의 slice() 같은 기본 복사 연산이 모두 얕은 복사를 만든다고 설명한다.[7]

전개 구문은 원본의 모든 특징을 그대로 복제하지도 않는다. 비열거 속성과 원본 프로토타입은 그대로 복사되지 않으며 접근자 속성은 읽힌 결과가 새 데이터 속성 값이 될 수 있다. Object.assign()은 대상 객체의 setter를 호출할 수 있어 전개 구문과 세부 동작도 완전히 같지 않다.[8] 문법이 짧다고 의미가 ‘객체 복제’ 하나로 단순해지지 않는다.

얕은 복사는 부족한 임시방편이 아니다. 바깥 상태만 교체하고 바뀌지 않은 하위 객체는 공유하는 불변 업데이트에서 매우 유용하다. 문제는 하위 객체까지 독립적이라고 오해하는 것이다. 어느 층을 새로 만들었는지 코드에서 보이게 해야 한다.

08 / A NEW LIST OF OLD OBJECTS

배열을 복사해도 요소가 연결될 수 있다

const copied = [...items] 또는 items.slice()는 새 배열을 만든다. copied.push()로 요소를 추가해도 원본 배열의 길이는 변하지 않는다. 여기까지만 보면 복사가 완벽해 보인다. 하지만 배열 칸에 객체가 들어 있다면 각 칸의 객체 값은 그대로 옮겨진다.

copied[0].price = 0을 실행하면 원본의 첫 상품에서도 가격 0이 보일 수 있다. 새로 생긴 것은 배열 컨테이너이고 상품 객체는 공유되기 때문이다. 반대로 copied[0] = { ...copied[0], price: 0 }처럼 첫 칸에 새 상품 객체를 넣으면 원본 배열의 첫 칸은 예전 객체를 유지한다.

중첩 배열도 같다. 행 배열을 복사했다고 각 행 배열까지 새로 생기지는 않는다. 2차원 격자에서 const board2 = [...board1] 뒤 한 칸을 바꾸면 공유된 행 배열 때문에 원본 보드도 바뀐다. 각 행도 복사하려면 board1.map(row => [...row])처럼 한 층 더 의도를 표현해야 한다.

하지만 깊이가 고정되지 않은 임의 객체에 전개 구문을 계속 중첩하는 것은 일반적인 깊은 복사 알고리즘이 아니다. 어떤 속성은 Date, Map, Set, ArrayBuffer일 수 있고 순환 참조도 있을 수 있다. 데이터 모양을 아는 경우의 선택적 복사와, 임의 그래프의 일반 복제를 구분해야 한다.

09 / REBUILDING THE GRAPH

깊은 복사는 그래프를 다시 그린다

깊은 복사는 원본과 복제본이 서로의 중첩 변경에 영향을 주지 않도록 연결된 가변 객체를 새로 구성하는 개념이다. 원본 A가 B와 C를 가리키고 B와 C가 같은 D를 공유한다면 단순히 각 경로를 따로 복사해서는 D가 두 개 생길 수 있다. 그래프 내부의 공유 관계까지 보존하려면 이미 처리한 원본 노드와 새 노드의 대응표가 필요하다.

순환은 더 분명한 시험이다. original.self = original인 객체를 무작정 재귀 복사하면 self를 따라 끝없이 다시 들어간다. 올바른 그래프 복제는 A의 복제본 A′를 먼저 기록하고 self에서 A를 다시 만났을 때 새로 복사하지 않고 A′를 연결한다. 그러면 clone.self === clone 관계가 살아남는다.

여기서 ‘깊다’는 무조건 모든 것을 똑같이 복제한다는 뜻이 아니다. 함수의 실행 환경, DOM 노드, 외부 파일 손잡이, 네트워크 소켓처럼 단순한 데이터 그래프로 재구성할 수 없는 값이 있다. 사용자 정의 클래스 인스턴스도 속성만 옮기면 원래 프로토타입의 동작과 불변 조건이 사라질 수 있다.

따라서 깊은 복사기는 지원하는 값의 종류와 보존하지 않는 의미를 문서화해야 한다. 도메인 객체라면 클래스가 직접 복제 방법을 제공하거나 명시적인 직렬화 형식을 정하는 편이 낫다. ‘아무 객체나 완벽히 복사’라는 버튼은 런타임의 모든 관계와 외부 자원을 설명할 수 없기 때문이다.

10 / THE STRUCTURED CLONE ALGORITHM

구조화 복제가 할 수 있는 일

브라우저의 structuredClone(value)는 WHATWG의 구조화 복제 알고리즘을 이용해 지원되는 값을 깊게 복사한다.[5] 평범한 객체와 배열뿐 아니라 Date, RegExp, Map, Set, ArrayBuffer 등 여러 내장 자료형을 다룰 수 있고 순환 참조도 보존한다. 메시지를 Worker나 다른 창으로 보낼 때 사용되는 구조화 직렬화 계열과 같은 기반을 공유한다.

복제 과정은 원본 객체 그래프를 그대로 다른 메모리 주소에 사진 찍듯 복사하는 일이 아니다. 지원되는 타입의 상태를 직렬화한 뒤 새 영역에서 역직렬화해 대응 객체를 만든다. 표준은 순환과 중복 참조를 처리하기 위한 메모리 대응 관계를 둔다. 복제본 안에서 하나였던 공유 하위 객체는 하나로 유지되어야 한다.

모든 값이 가능한 것은 아니다. 함수 같은 직렬화 불가능한 값이 그래프 안에 있으면 DataCloneError가 날 수 있다. 사용자 정의 속성 설명자, getter와 setter, 프로토타입 사슬을 원본 그대로 보존하는 범용 객체 복제라고 기대해서도 안 된다. MDN의 구조화 복제 문서는 지원되는 유형과 보존되지 않는 특성을 따로 설명한다.[6]

그래서 structuredClone()는 ‘지원되는 데이터 값의 독립 사본’이 필요할 때 알맞다. 실행 중인 동작과 자원까지 통째로 복제하려는 도구는 아니다. 폼 상태, 메시지 자료, 테스트 픽스처 같은 순수 데이터에는 유용하지만 대형 그래프를 매번 복제하면 시간과 메모리 비용도 함께 든다.

11 / JSON IS A DATA FORMAT

JSON 왕복은 만능 복사기가 아니다

JSON.parse(JSON.stringify(value))는 오랫동안 간단한 깊은 복사 요령으로 쓰였다. JSON으로 표현 가능한 평범한 객체와 배열만 있다면 새 객체가 만들어지고 중첩도 분리된다. 하지만 이것은 JavaScript 객체 복제 규칙이 아니라 JSON 데이터 형식으로 내보냈다가 다시 읽는 변환이다.

변환 과정에서 의미가 달라질 수 있다. Date는 toJSON()을 거쳐 문자열이 되고, Map과 Set은 별도 처리가 없으면 유용한 항목 구조가 그대로 나오지 않는다. 객체 속성의 undefined, 함수와 Symbol은 생략될 수 있으며 배열 안에서는 다른 형태로 바뀔 수 있다. BigInt는 기본 JSON 직렬화에서 오류가 난다. MDN도 JSON을 깊은 복사에 쓰려는 경우 순환 참조를 지원하는 structuredClone()을 고려하라고 안내한다.[9]

순환 객체는 기본 JSON.stringify()에서 오류를 낸다. 자기 자신으로 돌아오는 경로를 JSON 트리로 표현할 표준 참조 표기가 없기 때문이다. 반면 구조화 복제는 그래프 대응표를 이용해 순환을 다룬다. 트리 형식과 객체 그래프의 차이가 실제 오류로 나타나는 지점이다.

JSON 왕복이 나쁘다는 뜻은 아니다. 서버와 주고받을 공개 데이터 계약, 저장 가능한 스냅샷과 사람이 읽는 형식에는 매우 유용하다. 다만 어떤 값이 손실되거나 변환되는지 명시해야 한다. 복제가 목적이라면 자료형 보존 요구를 먼저 적고 도구를 선택해야 한다.

12 / MOVE OWNERSHIP, NOT BYTES

큰 데이터는 복사 대신 넘긴다

이미지 픽셀이나 오디오 덩어리처럼 큰 ArrayBuffer를 Worker로 보낼 때 매번 바이트 전체를 복사하면 시간과 메모리를 두 번 쓸 수 있다. 구조화 복제 API는 transfer 목록을 받아 일부 전송 가능 객체의 소유 자원을 복사본 쪽으로 넘길 수 있다. WHATWG 표준은 전송을 자원 소유권을 옮기고 원본 객체를 분리하는 동작으로 설명한다.[10]

structuredClone(data, { transfer: [buffer] }) 뒤에는 새 객체가 버퍼의 저장소를 사용할 수 있고 원본 buffer는 분리된다. 일반 ArrayBuffer라면 원본의 byteLength가 0이 되어 같은 바이트를 계속 쓰지 못한다. 이는 복사본을 하나 더 만든 것이 아니라 사용 권한을 한쪽에서 다른 쪽으로 이동한 결과다.

전송은 성능을 위한 마술이 아니라 소유권 계약이다. 보내는 쪽이 이후 그 버퍼를 읽지 않는다는 전제가 있어야 한다. 화면 그리기 파이프라인이나 Worker 작업 큐처럼 생산자에서 소비자로 책임을 넘기는 구조에는 잘 맞지만, 양쪽이 계속 같은 데이터를 써야 한다면 적합하지 않다.

공유 메모리는 또 다른 선택이다. SharedArrayBuffer처럼 복사도 전송도 아닌 공유가 필요한 경우에는 동기화와 보안 조건이 따라온다. 단순 대입, 얕은 복사, 깊은 복제, 전송, 공유는 서로 더 좋은 등급이 아니라 관계와 비용이 다른 도구다.

13 / COPY ONLY THE CHANGED PATH

안 바꾸는 습관과 구조 공유

상태 변경 버그를 줄이는 한 방법은 기존 객체를 직접 고치지 않고 새 상태를 만드는 규칙이다. 배송 도시만 바꾼다면 { ...item, shipping: { ...item.shipping, city: '원주' } }처럼 바뀌는 경로의 객체를 새로 만든다. item과 shipping은 새 객체가 되고, 바뀌지 않은 다른 하위 객체는 공유할 수 있다.

이 방식을 구조 공유라고 볼 수 있다. 전체 그래프를 매번 깊게 복제하지 않고 변경된 경로만 새로 만든다. 이전 상태는 그대로 남아 시간 여행 디버깅, 실행 취소, 변경 감지에 쓰기 쉽다. 참조 비교로 어느 가지가 바뀌었는지 빠르게 판단할 수 있다는 장점도 있다.

그러나 불변 업데이트도 자동으로 안전하지 않다. 복사해야 할 중첩 층을 하나 빠뜨리면 공유 객체를 다시 수정하게 된다. 객체 안에 Map이나 사용자 정의 클래스가 있으면 전개 구문만으로 의도를 지킬 수 없다. 상태 관리 도구가 구조 공유를 도와주더라도 외부에서 가변 객체를 끌어오면 경계가 새어 나올 수 있다.

모든 것을 깊은 복사하는 전략도 정답이 아니다. 큰 그래프를 자주 복제하면 할당량과 가비지 컬렉션 부담이 커지고 객체 동일성을 이용한 캐시가 매번 무효화된다. 필요한 독립성의 범위를 알고 변경 경로만 복사하거나, 정말 스냅샷이 필요할 때 구조화 복제를 선택하는 편이 낫다.

안전한 복사는 모든 것을 둘로 만드는 일이 아니다.
함께 살아야 할 것과 갈라져야 할 것을 정하는 일이다.

14 / FOLLOW THE ARROWS

네 가지 복사를 직접 따라가자

아래 체험은 실제 메모리 주소를 보여 주는 디버거가 아니라 관계를 설명하는 모형이다. 단순 대입, 객체 전개 얕은 복사, structuredClone(), ArrayBuffer 전송을 골라 단계별로 진행해 보자. 각각 무엇이 새로 생기고 무엇이 공유되며 원본이 계속 사용 가능한지가 달라진다.

단순 대입에서는 두 변수의 목적지가 처음부터 끝까지 같다. 얕은 복사에서는 바깥 객체만 분리되고 중첩 profile은 공유된다. 구조화 복제에서는 지원되는 객체 그래프가 새로 구성되고 복제본 내부의 순환은 복제본 안에서 닫힌다. 전송에서는 새 소유자가 자원을 얻는 대신 원본 버퍼가 분리된다.

체험의 객체 크기와 단계 수는 설명용이며 실제 JavaScript 엔진의 내부 명령 수나 메모리 배치를 측정한 것이 아니다. 결과 문장은 표준에서 관찰 가능한 관계를 단순화한다. 버튼을 눌러도 자료가 서버로 전송되거나 저장되지 않는다.

15 / DEBUG THE GRAPH

버그를 화살표로 추적하는 법

원본이 함께 바뀌는 버그를 만나면 먼저 값의 모양보다 동일성을 확인한다. 의심되는 두 변수에 a === b, a.shipping === b.shipping을 각각 적용하면 어느 층이 공유되는지 드러난다. 바깥은 다르지만 안쪽이 같다면 얕은 복사 경계를 찾은 것이다.

브라우저 개발자 도구에서는 객체를 나중에 펼쳤을 때 현재 값이 보일 수 있어 로그 시점의 스냅샷으로 오해하기도 한다. 재현에 필요한 작은 원시 값만 즉시 기록하거나, 지원되는 데이터라면 명시적으로 스냅샷을 만들고 시간 정보를 함께 남긴다. 무조건 JSON 문자열로 바꾸면 앞서 본 자료형 손실 때문에 다른 오해가 생길 수 있다.

테스트는 두 방향을 모두 확인해야 한다. 복제본의 중첩 속성을 바꾼 뒤 원본이 유지되는지, 원본을 바꾼 뒤 복제본이 유지되는지 본다. 순환과 공유 하위 객체, Date·Map 같은 실제 자료형이 있다면 그 관계도 검사한다. 전송을 쓴다면 원본 버퍼가 분리되는 것이 의도인지 명시적으로 확인한다.

코드 리뷰에서는 ‘복사했다’라는 설명 대신 연산을 구체적으로 쓴다. ‘새 배열을 만들고 요소 객체는 공유한다’, ‘shipping 경로까지 새로 만든다’, ‘구조화 복제로 순환 그래프를 분리한다’, ‘버퍼 소유권을 Worker로 넘긴다’처럼 적으면 숨은 전제가 줄어든다.

마지막으로 복사를 버그 수정용 주문처럼 남발하지 않는다. 원본 변경이 왜 문제인지, 누가 상태를 소유해야 하는지, 이후 양쪽이 독립적으로 변해야 하는지부터 정한다. 깊은 복사는 당장의 연결을 끊지만 데이터가 커졌을 때 성능과 일관성 문제를 새로 만들 수 있다.

16 / DECIDE THE RELATIONSHIP FIRST

복사 전에 관계부터 정하자

겹상자의 행사판이 원본 배송지까지 바꾼 이유는 복사 기능이 고장 나서가 아니었다. eventItem = originalItem이 객체를 만들지 않았고 두 이름이 같은 바깥 객체를 가리켰다. 전개 구문으로 바깥 객체만 새로 만들었더라도 shipping을 다시 만들지 않았다면 도시 객체는 계속 공유됐을 것이다.

단순 대입은 별칭을 만든다. 얕은 복사는 한 층의 컨테이너를 새로 만들고 중첩 객체 값을 공유할 수 있다. 구조화 복제는 지원되는 객체 그래프를 새로 구성하지만 함수와 모든 런타임 의미를 복제하지 않는다. JSON 왕복은 데이터 형식 변환이며 일부 값을 잃거나 바꾼다. 전송은 큰 자원의 소유권을 옮기고 원본 사용을 끝낸다.

따라서 복사 방법은 문법 취향이 아니라 관계 설계다. 원본과 결과가 이후 독립적으로 바뀌어야 하는가, 하위 객체 일부는 의도적으로 공유해도 되는가, 자료형과 순환을 보존해야 하는가, 비용 때문에 소유권을 넘겨도 되는가를 먼저 묻는다. 답이 정해지면 필요한 깊이와 도구가 보인다.

다음에 원본이 뜻밖에 바뀌면 컴퓨터가 두 상자를 헷갈렸다고 생각하지 말자. 변수에서 객체로, 객체에서 중첩 객체로 화살표를 그려 보자. 어디까지 새로 만들었고 어디부터 같은 노드를 보는지 찾으면 원인은 대개 그림 안에 있다. 복사는 데이터를 둘로 만드는 주문이 아니라 관계를 다시 그리는 작업이다.
