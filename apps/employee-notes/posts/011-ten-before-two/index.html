ISSUE 11 / RULES OF ORDER

가상의 수리 접수 서비스 ‘차곡’에는 작업 파일이 세 개 있었다. 이름은 파일1, 파일2, 파일10이었다. 담당자 다온이 ‘이름순’ 버튼을 누르자 화면은 파일1, 파일10, 파일2로 바뀌었다. 숫자가 작은 순서라면 틀린 결과처럼 보였지만, 글자를 왼쪽부터 비교한 결과라면 정확했다.

목록은 스스로 줄을 서지 않는다. 컴퓨터가 정렬하려면 두 항목을 받아 어느 것이 먼저인지 알려주는 규칙이 필요하다. 숫자로 볼지 글자로 볼지, 대소문자와 띄어쓰기를 구분할지, 한국어 규칙을 쓸지, 같은 값 사이에는 무엇을 다음 기준으로 삼을지 정해야 한다.

차곡·다온·수리 파일과 장애 장면은 설명을 위해 만든 가상 사례다. 실제 서비스의 기록이나 사용자 실험이 아니다. 기술 자료는 2026년 10월 4일 기준으로 확인했다. 아래 체험은 입력한 줄을 현재 브라우저의 JavaScript 비교 규칙으로 정렬하며 서버로 전송하거나 저장하지 않는다.

01 / TEN BEFORE TWO

번호표를 정렬했더니 1, 10, 2가 됐다

파일 이름을 한 글자씩 비교해 보자. ‘파일1’과 ‘파일10’은 앞의 세 글자와 숫자 1까지 같다. 한쪽 문자열이 거기서 끝나므로 짧은 파일1이 먼저 온다. 파일10과 파일2는 ‘파일’까지 같고 다음 글자 1과 2를 비교하므로 파일10이 먼저 온다. 이 규칙의 결과는 파일1, 파일10, 파일2다.

사람이 파일 이름 안의 숫자를 번호로 읽으면 다른 답을 기대한다. 접두어 ‘파일’을 떼고 1, 2, 10이라는 수를 비교하니 파일1, 파일2, 파일10이 자연스럽다. 두 결과 가운데 하나가 계산 실수인 것은 아니다. 입력을 문자열 전체로 보았는지, 문자열 안의 숫자 덩어리까지 해석했는지가 다르다.

버그는 대개 화면에 ‘이름순’이라고만 쓰여 있을 때 시작한다. 개발자는 기본 문자열 비교를 생각하고, 사용자는 번호가 포함된 자연 정렬을 생각한다. 요구사항의 한 단어가 서로 다른 비교 함수를 가리킨다. 정렬 결과를 고치려면 먼저 사용자가 기대한 순서를 문장과 예시로 꺼내야 한다.

차곡은 버튼 이름을 ‘이름순’에서 ‘번호를 포함한 이름순’으로 바꾸고 비교 규칙을 명시할 수 있다. 혹은 파일 번호를 이름 속에서 추측하지 않고 별도의 숫자 필드로 저장할 수 있다. 표시 문자열과 정렬용 데이터가 같은 값이어야 한다는 법은 없다.

02 / ORDER IS A QUESTION

정렬은 발견이 아니라 질문이다

키, 가격, 날짜처럼 순서가 당연해 보이는 값도 질문을 품는다. 키는 오름차순인가 내림차순인가. 가격은 할인 전인가 결제 금액인가. 날짜는 작성 시각인가 마지막 수정 시각인가. 같은 값은 먼저 들어온 순서인가 최근 활동 순서인가. ‘정렬해 줘’만으로는 답이 완성되지 않는다.

정렬 규칙은 각 항목에서 비교할 키를 고르고, 키 사이의 관계를 정의하며, 같은 키의 다음 기준을 정한다. 예를 들어 문의 목록을 ‘긴급도 내림차순, 접수 시각 오름차순, 접수 번호 오름차순’으로 적으면 세 번의 질문이 순서대로 작동한다. 앞 질문에서 차이가 나면 뒤 질문은 보지 않는다.

화면에 보이는 한 열만 기준이라고 생각해도 숨은 정책이 있다. 빈 값은 위로 올릴지 아래로 내릴지, ‘없음’이라는 문자열과 실제 결측값을 같은 것으로 볼지, 숫자 2와 문자열 "2"를 섞어도 되는지 결정해야 한다. 정렬은 데이터를 깨끗하게 만드는 기능이 아니라 데이터의 의미를 드러내는 기능이다.

따라서 테스트도 ‘정렬 버튼이 눌린다’로 끝나지 않는다. 1·2·10, 같은 값 두 개, 빈 값, 대소문자, 한글과 라틴 문자처럼 규칙의 경계를 드러내는 표본을 준비한다. 예상 목록을 먼저 적은 뒤 구현 결과와 비교해야 무엇이 어긋났는지 알 수 있다.

03 / THE DEFAULT

기본 정렬은 글자로 바꾸어 비교한다

JavaScript의 Array.prototype.sort()에 비교 함수를 주지 않으면 요소를 문자열로 바꾸고, 그 문자열을 UTF-16 코드 단위의 사전식 순서로 비교한다. 숫자 배열 [2, 10, 1]도 기본 정렬에서는 문자열 "2", "10", "1"처럼 다뤄져 [1, 10, 2]가 된다.[1]

이 동작은 이상한 예외가 아니라 명세에 적힌 기본값이다. 프로그램은 배열이 숫자만 담고 있다는 의도를 자동으로 제품 규칙으로 승격하지 않는다. 숫자 오름차순이 필요하면 (a, b) => a - b처럼 차이를 반환하는 비교 함수를 명시해야 한다.

기본값은 작은 예제에서는 숨어 있다. [1, 2, 3]은 문자열로 비교해도 숫자 순서와 같아 보인다. 10, 음수, 소수, 앞에 0이 붙은 값이 들어오는 순간 두 의미가 갈라진다. 정상 데이터만 넣은 시연이 정책 오류를 가려 버리는 셈이다.

sort()는 원래 배열 자체의 요소 순서를 바꾼다는 점도 중요하다.[1] 원본 목록을 다른 화면이나 상태 계산에서 계속 써야 한다면 복사본을 정렬하거나 원본을 바꾸지 않는 API를 선택해야 한다. ‘순서만 바꿨다’는 행위가 공유 상태에서는 데이터 변경이 될 수 있다.

04 / THE COMPARATOR

비교 함수는 두 항목의 관계를 답한다

비교 함수는 보통 a가 b보다 앞이면 음수, 뒤면 양수, 같은 순서로 취급하면 0을 반환한다. 정렬 알고리즘은 이 답을 여러 번 묻고 전체 목록을 배치한다. 함수가 최종 위치를 직접 지정하는 것이 아니라 두 항목의 관계를 일관되게 설명한다.

일관성이 깨지면 결과도 믿기 어렵다. a가 b보다 앞이고 b가 c보다 앞이라면서 c가 a보다 앞이라고 답하면 원처럼 순환한다. 같은 두 값을 비교할 때 실행할 때마다 답을 바꾸거나 외부 상태를 수정하는 함수도 알고리즘의 전제를 무너뜨린다. ECMAScript 명세는 정렬 비교자가 결정적이고 일관된 비교 관계를 제공해야 정상적인 정렬 순서를 기대할 수 있다고 설명한다.[1]

숫자를 뺀다는 짧은 표현에도 입력 검증이 필요하다. "없음"이나 undefined를 숫자로 바꾸면 NaN이 생길 수 있다. 거대한 정수와 정밀도가 필요한 식별자를 일반 Number로 바꾸면 서로 다른 값이 같아질 수도 있다. 비교 함수는 데이터 형식이 보장되는 경계 안에서 사용해야 한다.

복합 정렬은 비교 함수를 이어 붙인 형태다. 우선순위를 비교해 0이 아니면 그 결과를 쓰고, 0이면 접수 시각을 비교한다. 다시 0이면 고유 ID를 비교한다. 마지막 기준까지 쓰면 모든 항목의 위치를 재현할 수 있어 화면과 테스트, 페이지 나누기가 안정된다.

순서는 데이터에 숨어 있지 않다.

05 / NATURAL ORDER

자연 정렬은 숫자 덩어리를 숫자로 읽는다

파일2와 파일10을 사람이 기대하는 순서로 놓는 방식을 흔히 자연 정렬이라고 부른다. 문자열을 문자와 숫자 덩어리로 나누고, 대응하는 숫자 덩어리는 수의 크기로 비교한다. 운영체제 파일 목록과 제품 버전 목록에서 익숙한 결과를 만들 수 있다.

웹에서는 Intl.Collator에 numeric: true를 주어 지역화된 숫자 비교를 요청할 수 있다. ECMA-402는 Collator가 언어에 민감한 문자열 비교를 제공하고, numeric 옵션이 숫자 부분의 비교 사용 여부를 제어한다고 규정한다.[2] 이 글의 체험도 한국어 로캘의 Collator와 numeric 옵션을 사용한다.

그러나 ‘자연스럽다’는 말도 완전한 규칙은 아니다. 파일02와 파일2를 같은 것으로 볼지, 소수점과 마이너스 기호를 숫자에 포함할지, v1.10을 1.1로 오해하지 않을지 정해야 한다. 버전 문자열은 일반 숫자와 다른 문법을 가지므로 해당 버전 규칙에 맞는 비교기가 필요하다.

가장 안전한 방법은 의미 있는 숫자를 별도 필드로 보존하는 것이다. 화면에는 ‘접수 0002호’를 보여주면서 정렬은 정수 2로 할 수 있다. 이름에서 숫자를 다시 추출하는 방식은 입력 형식이 바뀌거나 여러 숫자가 들어올 때 정책이 흔들리기 쉽다.

06 / LANGUAGE ORDER

언어의 순서는 코드 포인트 순서가 아니다

문자열을 저장하는 번호 순서와 사전에서 기대하는 순서는 다를 수 있다. 대문자와 소문자, 악센트가 붙은 글자, 분해된 문자, 문장부호를 어느 단계에서 구분할지는 언어와 제품 목적에 따라 달라진다. 단순한 이진 비교가 모든 사람에게 자연스러운 가나다순이나 알파벳순을 보장하지 않는다.

Unicode Collation Algorithm은 문자열을 정규화하고 대조 요소와 여러 수준의 가중치로 바꾼 뒤 정렬 키를 비교하는 일반 구조를 제시한다. 라틴 문자 예에서는 기본 글자, 발음 구별 부호, 대소문자에 대응하는 여러 수준을 둘 수 있고, 언어별 요구에 맞게 규칙을 조정할 수 있다.[3]

Intl.Collator의 sensitivity 옵션은 기본 글자 차이, 악센트, 대소문자 가운데 어디까지 비교에 반영할지 선택하게 한다.[2] 검색 결과를 묶을 때와 사람 이름을 엄격히 정렬할 때 필요한 민감도가 다를 수 있다. 로캘을 생략해 실행 환경 기본값에 맡기면 사용자나 서버 환경에 따라 결과가 달라질 수 있으므로 재현성이 필요한 규칙은 로캘과 옵션을 명시한다.

정렬 규칙은 영원히 고정된 표도 아니다. Unicode 문서는 새 문자와 언어 정보, 표준 변경으로 대조 순서가 버전 사이에서 달라질 수 있으므로 버전을 주의 깊게 다뤄야 한다고 설명한다.[3] 정렬 키를 장기간 저장하거나 인덱스에 의존한다면 런타임과 대조 규칙의 갱신도 운영 사건이다.

07 / STABLE SORT

같다고 판단한 항목의 과거 순서를 지킨다

비교 함수가 두 항목에 0을 반환하면 둘은 현재 기준에서 동점이다. 안정 정렬은 이런 항목들이 정렬 전 서로 갖고 있던 순서를 유지한다. ECMAScript는 Array.prototype.sort가 안정 정렬이어야 한다고 명시한다.[1]

안정성은 여러 단계 정렬에서 유용하다. 먼저 이름순으로 정렬한 뒤 부서순으로 안정 정렬하면 같은 부서 안에서는 앞서 만든 이름순이 유지된다. 하지만 이 효과를 우연에 맡기기보다 하나의 비교 함수에 ‘부서, 이름, ID’ 순서를 명시하면 의도가 더 잘 드러난다.

안정 정렬과 결정적 정렬은 같은 말이 아니다. 입력 순서가 매번 달라지면 안정 정렬은 그 달라진 과거 순서를 그대로 보존한다. 결과를 어디서나 똑같이 만들려면 모든 동점을 끊는 마지막 키가 필요하다. Unicode Collation Algorithm도 안정 정렬은 알고리즘의 성질이고, 비교가 동점을 완전히 가르는 결정성과는 다르다고 구분한다.[3]

차곡의 접수 목록을 상태만으로 정렬하면 ‘수리 중’인 항목들이 들어온 순서대로 보일 수 있다. 한 브라우저에서는 괜찮아 보여도 서버가 다른 순서로 보내면 줄이 바뀐다. 상태 다음에 접수 시각과 고유 번호를 넣어야 제품이 원하는 재현 가능한 순서가 된다.

08 / DATABASE ORDER

ORDER BY가 없으면 저장 순서는 약속이 아니다

데이터베이스 테이블을 여러 번 조회했더니 늘 같은 순서로 나왔다고 하자. 그 순서는 삽입 순서처럼 보일 수 있다. 하지만 SQL 질의에 ORDER BY가 없다면 그 관찰을 계약으로 삼을 수 없다. PostgreSQL 문서는 정렬을 선택하지 않은 행은 지정되지 않은 순서로 반환되며, 스캔·조인 계획과 디스크의 순서에 따라 달라질 수 있다고 분명히 말한다.[4]

데이터가 작을 때는 순차 스캔이 우연히 물리 배치와 비슷한 결과를 낼 수 있다. 인덱스가 생기거나 통계가 바뀌고, 질의 계획이 달라지거나 병렬 처리가 켜지면 다른 경로가 선택된다. 데이터베이스가 망가진 것이 아니라 애초에 약속하지 않은 순서를 애플리케이션이 기대한 것이다.

ORDER BY를 추가해도 열의 자료형과 대조 규칙이 중요하다. text 열의 "10"과 "2"는 숫자 열의 10과 2처럼 비교되지 않는다. PostgreSQL에서는 ORDER BY에 적용되는 대조 규칙이 정렬 키의 collation에서 정해진다.[5] 화면 규칙과 데이터베이스 규칙이 다르면 서버 정렬과 브라우저 재정렬이 서로 다른 결과를 만들 수 있다.

인덱스는 요구한 ORDER BY를 별도 정렬 없이 제공할 수도 있지만, 인덱스가 있다는 사실 자체가 질의 결과의 순서 계약은 아니다. PostgreSQL은 B-tree 인덱스가 정렬된 출력을 만들 수 있고, 계획기가 인덱스 스캔과 명시적 정렬 가운데 비용에 따라 선택한다고 설명한다.[6] 결과 보장은 질의의 ORDER BY에 있고 실행 방법은 계획기에 있다.

어제도 같은 순서였다는 관찰은
내일도 같은 순서라는 계약이 아니다.

09 / TIES AND PAGES

동점 기준이 없으면 페이지 경계가 흔들린다

게시물을 작성 시각 내림차순으로 정렬하고 한 페이지에 열 개씩 보여 준다고 하자. 같은 시각을 가진 글이 여러 개라면 그 사이의 순서는 정해지지 않았다. 첫 요청에서는 A가 10번째이고 B가 11번째였지만 다음 요청에서 둘이 바뀌면 사용자는 B를 두 번 보거나 A를 놓칠 수 있다.

PostgreSQL의 LIMIT/OFFSET 문서는 결과 행의 어떤 부분집합을 선택할 때 ORDER BY로 유일한 순서를 강제하지 않으면 예측할 수 없는 부분집합을 얻을 수 있다고 경고한다.[7] LIMIT 값이 달라지면 계획이 달라져 서로 다른 순서가 나올 수도 있다.

해결은 정렬 키를 완전하게 만드는 것이다. 작성 시각이 같을 때 고유 ID 내림차순을 추가해 ORDER BY created_at DESC, id DESC처럼 쓴다. 다음 페이지 커서에도 두 값을 함께 넣으면 마지막으로 본 위치 뒤를 정확히 이어 갈 수 있다. ID 하나만 커서로 쓰면서 표시 순서는 날짜로 두면 두 규칙이 어긋난다.

목록을 보는 동안 새 데이터가 들어오거나 기존 값이 바뀌는 문제는 별도다. 완전한 정렬은 같은 데이터 집합에서 위치를 결정하지만, 페이지 사이에 집합 자체가 변하면 스냅샷이나 커서 정책이 필요할 수 있다. 정렬 키와 읽기 일관성은 함께 설계하되 같은 문제로 뭉개지 않는다.

10 / MISSING VALUES

빈 값과 잘못된 숫자도 자리가 필요하다

정렬할 열에 값이 없는 항목이 들어오면 ‘비교할 수 없으니 제외’가 자동 정답은 아니다. 미정 배송일을 가장 위에 보여 담당자가 처리하게 할 수도 있고, 날짜순 목록의 맨 아래에 둘 수도 있다. NULLS FIRST와 NULLS LAST처럼 결측값의 위치는 제품 정책이다.[4]

빈 문자열, null, 필드 없음, 0은 서로 다른 상태일 수 있다. 모두 falsy라는 이유로 한 덩어리로 만들면 ‘수량 0’이 ‘아직 입력하지 않음’과 같은 자리에 놓인다. 정렬 전에 데이터 모델에서 각 상태의 의미를 분리하고 비교 함수가 그 의미를 드러내게 해야 한다.

숫자처럼 보이는 문자열을 숫자로 바꿀 때도 실패 경로를 정한다. "12개"를 12로 읽을지 오류로 볼지, 쉼표가 있는 "1,000"을 어떤 로캘 문법으로 해석할지 결정한다. Intl.Collator는 비교 도구이지 임의 문자열을 안전한 업무 숫자로 검증하는 파서가 아니다.

잘못된 값을 조용히 0으로 바꾸면 목록은 정돈되어 보여도 오류가 정상 데이터 사이에 숨는다. 차곡은 숫자로 해석할 수 없는 번호를 맨 아래의 ‘확인 필요’ 구역에 모으고 원본 문자열을 보여줄 수 있다. 사용자는 순서뿐 아니라 왜 그 자리에 왔는지도 이해해야 한다.

11 / COST OF ORDER

정렬 결과와 정렬 비용은 다른 문제다

n개 항목을 비교 정렬하면 일반적으로 많은 쌍 비교가 필요하다. 비교 함수 안에서 매번 복잡한 날짜 파싱, 문자열 정규화, 네트워크 요청을 하면 알고리즘보다 비교 키 계산 비용이 더 커질 수 있다. 바뀌지 않는 키는 한 번 계산해 보관하고 정렬에서는 그 키를 비교하는 방식이 유리하다.

데이터베이스는 전체 행을 정렬하거나, 요구 순서와 맞는 B-tree 인덱스에서 앞부분만 읽을 수 있다. 특히 ORDER BY와 LIMIT가 함께 있을 때 맞는 인덱스는 나머지를 모두 스캔하지 않고 첫 n개를 가져올 수 있다고 PostgreSQL 문서가 설명한다.[6] 하지만 쓰기 비용과 저장 공간이 늘어나므로 모든 조합에 인덱스를 만들 수는 없다.

브라우저로 수십만 행을 받아 정렬한 뒤 스무 개만 보여 주는 구조는 네트워크와 메모리를 낭비한다. 반대로 서버가 사용자 로캘을 모르는 상태에서 이름을 정렬하면 화면의 언어 기대와 다를 수 있다. 데이터 크기, 페이지 방식, 동일한 결과를 여러 사용자가 공유해야 하는지에 따라 정렬 위치를 고른다.

최적화 전에는 먼저 정답 규칙을 고정한다. 잘못된 순서를 빠르게 만드는 것은 개선이 아니다. 대표 데이터로 결과를 검증하고, 실행 계획과 실제 비용을 측정한 뒤 인덱스·키 캐시·서버 정렬을 선택한다. 비교 횟수만 보고 사용자에게 중요한 로캘 규칙을 버리지 않는다.

12 / LAB GUIDE

세 가지 자로 같은 목록을 재 보자

아래 체험의 입력 칸에는 한 줄에 한 항목을 넣는다. ‘예시 채우기’는 파일2, 파일10, 파일1과 같은 값을 준비한다. 문자열순은 JavaScript 기본 정렬처럼 UTF-16 코드 단위의 사전식 비교를 사용한다. 숫자 포함 이름순은 한국어 Intl.Collator에 numeric: true를 준다.

순수 숫자순은 줄 전체가 유한한 숫자로 해석되는 항목을 먼저 수의 크기로 비교하고, 숫자가 아닌 항목은 뒤에서 이름순으로 정리하는 이 체험만의 명시적 규칙이다. 업무 화면이 꼭 이 정책을 써야 한다는 뜻은 아니다. 세 열을 나란히 보며 규칙이 결과를 어떻게 바꾸는지 확인하기 위한 모형이다.

같은 문장을 두 번 넣으면 결과 옆의 원래 줄 번호가 유지되는 것도 볼 수 있다. 현재 JavaScript의 안정 정렬에서는 비교 결과가 0인 항목의 입력 순서가 보존된다. 그러나 원본 입력 순서가 서버마다 다르다면 최종 목록도 달라질 수 있으므로 결정적인 결과에는 별도 동점 키가 필요하다.

빈 입력, 20줄 초과, 한 줄 60자 초과는 오류로 표시한다. 입력은 이 페이지 안에서만 계산하고 저장하거나 전송하지 않는다. 이 체험은 현재 브라우저가 제공하는 국제화 데이터의 결과이며 모든 운영체제와 데이터베이스의 대조 순서가 같다고 보증하지 않는다.

13 / WRITE THE RULE

정렬 규칙을 제품의 문장으로 적자

첫째, 표시 이름이 아니라 사용자의 목적을 적는다. ‘최신순’은 작성 시각인지 수정 시각인지, 예약 공개 시각인지 분명히 한다. ‘이름순’은 로캘과 대소문자·숫자 처리 예시를 붙인다. 파일1, 파일2, 파일10의 기대 순서를 쓰는 순간 모호함이 줄어든다.

둘째, 자료형을 보존한다. 수량과 접수 번호를 문자열 이름 속에만 넣지 말고 숫자 필드로 저장한다. 날짜는 파싱되지 않은 표시 문자열이 아니라 명확한 시간 값과 필요한 지역 정보를 보존한다. 화면 형식이 바뀌어도 정렬 의미가 유지된다.

셋째, 모든 동점을 끊을 필요가 있는지 판단한다. 단순한 한 화면 목록에서 안정 정렬만으로 충분할 수 있지만, 페이지 나누기·캐시·서버 간 재현이 필요하면 고유 ID 같은 마지막 키를 추가한다. SQL과 브라우저가 같은 키와 방향을 쓰는지도 확인한다.

넷째, 결측값과 오류의 자리를 정한다. 빈 값이 위인지 아래인지, 잘못된 값은 숨기는지 별도 구역에 표시하는지 제품 행동으로 합의한다. 조용한 형 변환으로 문제를 0이나 빈 문자열에 섞지 않는다.

다섯째, 경계 표본을 회귀 테스트로 남긴다. 1·2·10, 같은 키, 대소문자, 조합이 다른 동일 문자, null, 잘못된 숫자, 한 페이지 끝의 동점을 포함한다. 대조 라이브러리나 데이터베이스를 갱신할 때 이 표본이 의도한 순서를 지키는지 다시 확인한다.

14 / ENDING

순서가 틀린 것이 아니라 규칙이 숨었다

차곡의 파일10은 파일2를 이기려던 것이 아니다. 프로그램은 이름 전체를 글자로 비교하라는 기본 규칙을 따랐다. 다온이 기대한 것은 이름 속 숫자를 수로 읽는 다른 규칙이었다. 화면의 ‘이름순’이라는 짧은 말이 두 생각을 같은 것처럼 보이게 했다.

문자열은 코드 단위로도, 언어별 대조 규칙으로도, 숫자 덩어리를 해석하는 자연 정렬로도 비교할 수 있다. 안정 정렬은 동점의 과거 순서를 보존하지만 결과를 세계 어디서나 같게 만들지는 않는다. 데이터베이스도 ORDER BY가 없으면 행의 순서를 약속하지 않는다.

정렬은 장식이 아니다. 어떤 항목이 먼저 보이고 어떤 작업이 뒤로 밀리는지 정하는 제품의 정책이다. 고객 문의, 작업 대기열, 가격표, 검색 결과에서 순서는 사용자의 판단과 행동을 바꾼다. 그래서 비교 규칙은 코드 한 줄이기 전에 설명할 수 있는 문장이어야 한다.

다음에 목록이 이상하게 보이면 컴퓨터가 숫자를 모른다고 화내기 전에 물어보자. 이 값은 숫자인가 이름인가. 같은 값은 무엇으로 가를 것인가. 어느 언어의 규칙인가. 순서가 틀린 것이 아니라, 우리가 선택한 규칙이 화면 뒤에 숨어 있었을지 모른다.
