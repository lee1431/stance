설명을 위해 가상의 공동 작업 웹앱 ‘함께보드’를 사용하자. 지민은 자기 문서를 읽고 수정할 수 있고, 다른 사람의 비공개 문서는 열 수 없다. 이 글의 이름, 문서, 세션 상태와 체험은 원리를 보여주는 가상 설정이다. 실제 계정을 사용하거나 서비스의 인증 기능을 측정한 결과가 아니다. 중심 사례는 서버에 세션 정보를 보관하고 브라우저에는 식별자를 전달하는 방식이다.

오늘의 질문은 이것이다. 한 번 확인한 신원을 다음 요청까지 연결하려면 무엇을 주고받아야 하며, 그 연결은 언제 끝나야 하는가? 비밀번호를 확인하는 순간, 쿠키를 저장하는 순간, 서버가 요청의 주체를 찾는 순간, 문서를 열도록 허용하는 순간은 서로 다른 단계다. 로그인 표시 하나 뒤의 연결을 따라가 보자.

01 / A NAME ON THE SCREEN

내 이름이 보이는 것과 서버가 나를 확인한 것은 다르다

함께보드의 화면에는 ‘지민 님’이라고 적혀 있다. 그 문장을 바꾸는 것은 브라우저의 JavaScript만으로도 가능하다. 개발 도구에서 글자를 바꾼다고 서버의 계정 정보까지 바뀌지는 않는다. 이 간단한 구분이 로그인 기능의 출발점이다. 화면의 이름은 사용자에게 상태를 설명하는 표시이고, 서버는 별도의 근거로 요청을 판단해야 한다.

HTTP 요청에는 원하는 주소와 여러 헤더, 경우에 따라 본문이 들어간다. HTTP 자체가 앞의 로그인 요청을 자동으로 이어 붙여 사용자를 기억해 주는 것은 아니다. 쿠키는 이런 요청들 사이에서 작은 상태 정보를 주고받는 수단으로 사용된다. 브라우저가 받은 쿠키를 이후 조건에 맞는 요청에 붙이면 서버는 연결할 단서를 얻는다. [1]

여기서 ‘연결’은 계속 열린 전화선과 다르다. 문서를 요청할 때마다 서버에 근거가 전달될 수 있다. 페이지가 잠깐 닫혔다가 다시 열려도 조건이 맞는 쿠키와 유효한 세션이 남아 있으면 관계를 이어갈 수 있다. 반대로 네트워크 연결이 멀쩡하고 같은 화면을 보고 있어도 세션이 끝났다면 다음 요청은 거절될 수 있다.

인터넷 주소만으로 사용자를 알아보려는 생각도 충분하지 않다. 여러 사람이 같은 공유기를 쓰고, 한 사람도 와이파이와 이동통신을 오갈 수 있다. 주소는 진단의 단서가 될 수 있지만 계정을 확인하는 약속과 동일하지 않다. 함께보드가 확인해야 할 대상은 ‘같은 위치에서 온 요청’이 아니라 ‘지민의 유효한 로그인 관계를 가진 요청’이다.

02 / CHECKING THE CLAIM

비밀번호 확인은 관계를 시작하는 단계다

처음 로그인할 때 지민은 자기 계정이라고 주장하고, 그 주장을 뒷받침하는 비밀번호를 제출한다. 서버는 등록된 계정의 인증 정보와 비교해 확인한다. 비밀번호는 평문으로 보관해 단순 비교하는 대신 목적에 맞는 비밀번호 해시 방식으로 처리해야 한다. OWASP의 비밀번호 저장 문서는 전용 해시 알고리즘과 솔트 사용을 설명한다. [2]

이 글에서 중요한 것은 그 확인을 매 페이지마다 그대로 반복하지 않는다는 점이다. 도서관에서 회원 확인을 한 뒤 이용표를 받는 장면을 떠올려 보자. 매 서가 앞에서 회원 가입 서류를 다시 내는 대신, 이미 확인된 이용 관계를 보여주는 표를 사용한다. 웹의 로그인도 처음의 확인 뒤에 다음 요청을 연결할 별도의 수단을 만들 수 있다.

비유에서 이용표는 편의를 주지만 새 책임을 만든다. 표를 다른 사람이 가져가면 누가 이용했는지 잘못 판단할 수 있다. 비밀번호를 매번 보내지 않게 되었다고 인증과 관련된 중요한 정보가 사라진 것은 아니다. 대신 세션 식별자 같은 다른 정보가 그 관계를 대표한다. 대표물이 어디에 보관되고 누구에게 전달되는지를 살펴야 한다.

또한 로그인 절차는 모든 제품에서 비밀번호 하나로 끝나는 것은 아니다. 추가 인증이나 다른 인증 수단을 사용하는 경우도 있다. OWASP는 인증과 재인증을 위험 수준에 맞춰 다루도록 설명한다. [3] 함께보드의 가상 사례는 한 가지 출발 경로를 사용하지만, 이후 요청을 연결하고 권한을 판단하는 문제는 다른 인증 수단을 써도 남는다.

03 / A REFERENCE TO A RELATIONSHIP

세션 식별자는 사람의 이름보다 보관함의 번호에 가깝다

인증에 성공한 함께보드는 서버에 로그인 관계를 만든다. 이 사례에서는 임의의 식별자와 계정, 시작 시각, 만료 규칙을 연결해 보관한다. 브라우저에는 그 관계를 찾는 식별자를 전달한다. 다음 요청에서 서버는 식별자로 보관함을 찾아 어떤 계정의 관계인지 확인한다. 브라우저가 계정의 모든 권한을 스스로 선언하는 방식과는 다르다.

식별자가 단순히 ‘지민’이나 순서대로 증가하는 번호라면 다른 값을 추측하기 쉽다. 서버에서 관리하는 세션의 식별자는 의미 없는 값으로 만들고 예측하기 어렵게 생성하는 것이 중요하다. 인증 뒤에는 식별자를 갱신해 로그인 이전의 식별자와 연결된 위험을 줄인다. OWASP의 세션 관리 문서가 설명하는 기본 원칙이다. [4]

이 글의 그림에서는 식별자를 ‘표 A’라고 부른다. 읽기 쉬운 모형의 이름일 뿐, 실제 서비스에서 사용할 비밀 값이 아니다. 표 A를 알면 지민의 관계를 찾을 수 있다는 조건 때문에 실제 값은 함부로 화면이나 로그에 드러내지 않아야 한다. 식별자가 개인정보처럼 생기지 않았다고 중요하지 않은 데이터가 되는 것은 아니다.

보관함의 번호라는 비유에도 한계가 있다. 정상 요청이 번호를 제시했다고 해서 그 순간 화면 앞의 사람이 반드시 지민이라는 사실을 새로 입증한 것은 아니다. 서비스는 그 번호를 가진 유효한 관계를 신뢰한다. 그래서 탈취와 오용을 줄이는 보호, 만료, 필요한 작업에서의 추가 확인이 함께 필요하다. 한 번 발급된 관계를 무조건 영원히 신뢰하는 설계는 질문의 절반만 다룬다.

04 / THE BROWSER CARRIES THE NOTE

쿠키는 조건에 맞는 요청에 번호를 실어 보낸다

서버는 응답의 Set-Cookie 헤더로 브라우저에 쿠키 저장을 요청할 수 있다. 브라우저는 쿠키 정책에 따라 이를 보관하고, 적용되는 요청에 Cookie 헤더를 붙인다. RFC 6265는 이 두 헤더를 이용한 상태 관리의 기본 구조를 정의한다. [5] 쿠키가 세션 그 자체라기보다 세션을 찾는 정보를 운반할 수 있는 수단이라는 구분이 여기서 생긴다.

함께보드의 문서 목록 페이지는 비밀번호를 알 필요가 없다. 브라우저가 적용되는 쿠키를 보내고 서버가 관계를 확인하면 된다. 페이지 코드가 매번 식별자를 읽어 요청 본문에 복사해야만 로그인 상태가 유지되는 것도 아니다. 브라우저의 자동 전달 기능은 편리하지만, 개발자가 의도한 범위와 브라우저가 적용한 범위가 맞는지 확인해야 한다.

예를 들어 로그인 응답에서 쿠키를 저장하려 했는데 브라우저가 받아들이지 않았다면, 이름을 보여주는 첫 화면만 바뀌고 다음 문서 요청은 로그인 상태를 잃을 수 있다. ‘로그인 버튼은 성공했다’는 관찰만으로 전체 연결이 완성됐다고 말할 수 없다. 응답에서 쿠키가 설정됐는지, 실제로 저장됐는지, 다음 요청에 포함됐는지를 나눠 확인한다.

반대로 쿠키가 저장되어 있다고 서버에 유효한 관계가 반드시 남아 있는 것도 아니다. 브라우저는 번호를 갖고 있지만 서버는 이미 그 번호를 무효화했을 수 있다. 쿠키가 있다는 사실은 브라우저가 무엇을 보관하는지 알려 주고, 세션이 유효하다는 사실은 서버가 현재 무엇을 인정하는지 알려 준다. 둘 중 하나만 보는 진단은 상태의 반쪽을 놓친다.

05 / WHICH REQUEST GETS THE COOKIE

보관된 쿠키가 모든 주소로 나가는 것은 아니다

쿠키에는 전달 범위와 조건이 있다. Domain을 생략하면 설정한 호스트에 한정되는 쿠키가 되고, Path는 요청 경로의 적용 범위를 정한다. Secure는 HTTPS 전송 조건에 사용된다. 경로 범위는 서버 전송을 조절하는 기능이지 같은 사이트의 코드 사이에 강한 보안 벽을 세우는 기능은 아니다. [6]

함께보드가 화면과 API를 서로 다른 호스트에 두었다고 가정하자. 화면에 로그인 이름이 보인다고 API 요청에도 같은 쿠키가 실렸다고 추측할 수 없다. 어디서 쿠키를 설정했고 어느 주소로 요청했는지 먼저 적어야 한다. 이름이 비슷한 두 호스트라도 브라우저가 보는 요청 조건은 다를 수 있다.

fetch() 요청의 credentials 설정도 관련된다. 기본값은 같은 출처의 요청에 자격 증명을 포함하는 same-origin이며, 다른 출처를 포함하는 요청에는 다른 설정을 검토하게 된다. 하지만 include를 골라도 쿠키의 적용 조건과 브라우저 정책까지 무시하는 것은 아니다. [7] 옵션 한 줄을 로그인 성공 버튼처럼 생각하면 원인을 더 숨길 수 있다.

이 글에서는 앞선 메시지 전달 편의 CORS 설명을 반복하기보다, 어떤 근거가 요청에 실제로 실렸는지에 집중한다. 응답이 읽히는 문제와 인증 정보가 전달되는 문제는 각각 확인한다. 개발 도구에서 주소와 쿠키의 조건을 비교하면 ‘한 페이지에서는 되는데 다른 페이지에서는 안 된다’는 현상을 구체적인 범위 차이로 바꿀 수 있다.

범위는 넓힐수록 편해 보일 수 있다. 그러나 필요 없는 호스트까지 같은 인증 정보를 공유할 이유는 별도로 설명해야 한다. 함께보드에서 문서 API가 필요한 관계와 홍보 페이지가 필요한 관계는 같지 않을 수 있다. 가장 넓은 범위를 먼저 주는 것보다, 실제로 관계를 사용하는 경로를 정하고 그 범위에 맞추는 편이 이해하기 쉽다.

06 / KEEPING THE REFERENCE OUT OF SCRIPTS

JavaScript가 읽지 못해도 요청에는 실릴 수 있다

HttpOnly가 붙은 쿠키는 페이지 JavaScript가 document.cookie로 읽을 수 없지만 적용되는 HTTP 요청에는 전달될 수 있다. 그래서 페이지 코드가 식별자를 직접 볼 수 없는데도 로그인 기능이 동작하는 것은 모순이 아니다. 브라우저가 보관하고 운반하는 기능과 스크립트에 값을 공개하는 기능이 분리되어 있기 때문이다. [6]

개발자가 콘솔에서 번호를 볼 수 없다고 오류라고 판단하면 불필요하게 보호를 풀 수 있다. 함께보드의 화면은 지민의 이름과 표시할 문서 목록만 필요하고, 비밀 식별자를 알아야 할 이유는 없다. 서버에서 확인한 최소 상태를 화면에 알려주고, 인증 정보를 운반하는 역할은 브라우저와 서버의 약속에 맡길 수 있다.

그렇다고 HttpOnly가 모든 스크립트 문제를 해결하지는 않는다. 악성 코드가 같은 페이지에서 실행된다면 식별자를 읽지 못해도 사용자 권한으로 요청을 발생시키거나 보이는 데이터를 다룰 수 있다. 이 속성은 중요한 보호의 한 부분이며, 페이지에 신뢰하지 않는 코드를 실행시키지 않는 설계까지 대신하지 않는다.

다른 저장소에 식별자를 넣으면 어떻게 될까. localStorage는 쿠키처럼 요청에 자동 첨부되는 저장소가 아니고, 같은 출처의 JavaScript가 접근할 수 있다. OWASP의 HTML5 보안 문서는 세션 식별자를 이곳에 보관하는 위험을 지적한다. [8] 단지 사용하기 쉽다는 이유만으로 저장 위치를 정하면, 전달 방법과 노출 범위를 함께 바꾸게 된다.

07 / A REQUEST IS NOT THE SAME AS INTENT

자동으로 실린 번호는 사용자의 의도까지 증명하지 않는다

쿠키가 조건에 맞는 요청에 자동으로 실리는 기능은 또 다른 질문을 만든다. 브라우저가 함께보드로 요청을 보냈다고 해서 지민이 그 작업을 직접 의도했는가. 외부 페이지가 사용자의 브라우저를 통해 상태를 바꾸는 요청을 유발하는 상황을 고려해야 한다. 이런 의도와 요청의 어긋남을 다루는 문제가 CSRF, 사이트 간 요청 위조다.

함께보드에서 문서를 지우는 작업을 생각해 보자. 유효한 세션 번호만 보고 삭제를 허용한다면, 번호가 실린 요청이 어떻게 시작됐는지를 충분히 살피지 못할 수 있다. 서버는 상태 변경 요청에 적절한 CSRF 방어를 적용하고, 필요에 따라 요청 출처나 별도 토큰 같은 근거를 확인한다. SameSite는 도움이 되지만 보통의 구현에서 모든 CSRF 방어를 대신한다고 가정해서는 안 된다. [9]

이 설명에서 세션 번호와 CSRF 토큰은 같은 질문에 답하지 않는다. 세션 번호는 어느 로그인 관계에 연결할지를 찾고, CSRF 방어는 브라우저의 자동 자격 증명 전달이 의도하지 않은 작업으로 이어지는 위험을 줄인다. 두 값의 이름이 모두 토큰이라고 해서 서로 대체할 수 있는 것은 아니다. 어떤 실패를 막으려는 값인지 먼저 적어야 한다.

제품 화면에는 삭제 확인 문구가 있을 수 있다. 하지만 그 화면을 거쳤다는 사실을 서버가 자동으로 알지는 못한다. 화면에 확인 버튼을 만드는 일과 서버가 요청의 근거를 검증하는 일을 함께 설계한다. 사용자가 보는 친절한 절차가 서버의 허용 규칙과 연결되어야, 절차를 보지 않은 요청에도 같은 기준을 적용할 수 있다.

작은 상태 모형 / 실제 계정과 쿠키는 사용하지 않습니다

브라우저가 보내는 정보와 서버의 관계를 고른 뒤 문서 요청을 눌러 보세요. 모형의 판단이며 실제 HTTP 요청이나 로그인을 수행하지 않습니다.

08 / WHO AND WHAT ARE DIFFERENT QUESTIONS

나를 알아봤다고 모든 문을 열어 주지는 않는다

함께보드는 표 A를 받아 지민의 유효한 로그인 관계를 찾았다. 이제 지민이 요청한 문서를 열 수 있는지 판단해야 한다. 신원을 확인하는 인증과 자원에 대한 작업을 허용하는 인가는 다른 질문이다. OWASP는 권한을 모든 요청에서 검증하고 기본적으로 허용 범위를 제한하는 원칙을 설명한다. [10]

지민의 화면에서 남의 문서를 여는 버튼을 숨기는 것은 사용 경험을 정리하는 데 도움이 된다. 그러나 누군가 문서 주소를 직접 요청했을 때도 서버가 같은 기준으로 거절해야 한다. 버튼이 보이지 않는다는 사실은 브라우저 화면의 조건이고, 문서를 내주지 않는다는 사실은 서버의 조건이다. 둘을 바꾸어 생각하면 로그인만 된 사람에게 불필요한 접근을 허용하게 된다.

권한에는 작업의 종류도 있다. 읽을 수 있는 문서를 수정할 수 있는가, 수정할 수 있는 문서를 삭제할 수 있는가. 함께보드가 공동 작업자를 초대했다면 보기만 허용한 관계와 편집까지 허용한 관계를 구분할 수 있다. 같은 문서와 같은 계정이어도 요청한 행동에 따라 결과가 달라진다.

회사나 모임을 여러 개 지원하는 제품에서는 소속의 경계도 중요하다. 지민이 A모임의 운영자라고 B모임의 운영자까지 되는 것은 아니다. 역할 이름만 확인하는 대신 요청한 문서의 소속과 현재 계정의 관계를 연결해 판단한다. ‘관리자’라는 단어가 넓어질수록 어느 범위의 관리자라는 설명이 필요하다.

거절 응답을 어떤 상태 코드와 문구로 표현할지는 제품 정책에 맞춘다. 로그인 관계를 못 찾은 경우와 관계는 찾았지만 문서 권한이 없는 경우는 내부에서 구분하되, 비공개 문서의 존재를 불필요하게 알려주지 않도록 응답을 설계할 수도 있다. 위 체험은 원리를 드러내기 위해 두 결과를 분리해 보여주는 모형이다.

09 / TWO CLOCKS FOR A RELATIONSHIP

쿠키의 수명과 서버의 인정 기간은 다를 수 있다

브라우저 쿠키에는 만료 조건을 둘 수 있다. 만료 시각이나 지속 시간을 정한 쿠키와 그렇지 않은 세션 쿠키가 있으며, 브라우저의 세션 복원 기능 때문에 창을 닫았다는 사실만으로 쿠키가 반드시 사라졌다고 단정할 수는 없다. MDN은 이런 수명과 복원 동작을 설명한다. [1] ‘브라우저를 닫으면 로그아웃’이라는 문구는 실제 구현과 맞는지 확인해야 한다.

서버에도 관계를 인정하는 기간이 있다. 브라우저가 번호를 보관해 보내더라도 서버가 만료된 것으로 판단하면 문서를 내주지 않는다. 반대로 브라우저가 번호를 잃으면 서버에 관계가 남아 있어도 그 브라우저의 요청을 연결하기 어렵다. 두 곳의 시계가 같은 의미를 갖는다고 가정하지 않는 것이 중요하다.

함께보드의 가상 규칙으로 ‘오랫동안 활동하지 않으면 종료’와 ‘활동을 계속해도 일정 시간이 지나면 다시 확인’을 구분해 보자. 전자는 마지막 활동을 기준으로 하고 후자는 관계의 시작을 기준으로 한다. 어느 기준을 쓰는지에 따라 계속 작업하는 사용자와 자리를 오래 비운 사용자에게 다른 경험이 생긴다. 이 글은 구체적인 시간값을 모든 제품에 맞는 기준으로 제시하지 않는다.

시간이 끝나는 순간 작성 중인 문장이 사라지면 보안 규칙은 맞아도 제품은 불친절하다. 로그인 관계가 끝났다는 사실과 사용자가 편집한 내용을 버릴지 여부는 따로 다룰 수 있다. 다시 인증할 길을 제공하고, 필요한 경우 초안 보존 여부를 명확히 안내한다. 관계의 수명을 설계할 때는 종료 이후 사람이 작업을 이어갈 방법도 함께 생각한다.

10 / ENDING THE AGREEMENT

로그아웃은 화면에서 이름을 지우는 것보다 크다

지민이 로그아웃 버튼을 눌렀다. 함께보드는 이름을 지우고 첫 화면으로 이동했다. 이것만 했다면 브라우저에 남은 번호로 다음 요청이 여전히 허용될 수 있다. 서버 세션 방식에서는 서버 쪽 관계를 무효화하고 브라우저 쪽 쿠키도 올바른 범위로 제거하는 절차가 필요하다. OWASP의 세션 관리 문서는 로그아웃과 만료 시 서버 쪽 무효화를 강조한다. [4]

쿠키를 제거할 때는 설정할 때의 이름과 범위를 맞춰 만료시키는 방법을 사용한다. 이름만 같고 경로나 도메인 조건이 다르면 의도한 쿠키를 없애지 못할 수 있다. [5] 그래서 로그아웃 테스트는 화면의 문구만 보지 않는다. 종료한 뒤 보호된 문서를 다시 요청했을 때 서버가 어떻게 응답하는지 확인한다.

다른 탭이 열려 있었다면 그 탭에는 오래된 이름과 문서가 남아 있을 수 있다. 그 화면이 새 요청의 허용을 증명하지는 않는다. 다음 보호 요청에서는 끝난 관계를 인정하지 않아야 한다. 탭 사이에 종료 상태를 알려 표시를 정리할 수도 있지만, 서버의 판단을 탭 알림만으로 대신할 수는 없다.

이미 사용자에게 전달된 문서 내용까지 로그아웃이 시간 거꾸로 되돌려 회수하는 것은 아니다. 화면과 메모리, 제품이 저장한 사본에는 별도의 수명 문제가 있다. 중요한 내용이라면 종료 때 어떤 표시와 로컬 사본을 정리하는지 정책을 정해야 한다. ‘새 접근을 막는다’와 ‘이미 받은 내용을 지운다’는 서로 다른 약속이다.

또한 이 기기만 로그아웃하는 기능과 모든 기기의 관계를 종료하는 기능은 범위가 다르다. 함께보드가 지민의 태블릿과 휴대전화에 각각 관계를 만들었다면 하나를 끝냈다고 다른 것까지 자동으로 끝나지는 않는다. 사용자가 선택한 종료 범위와 서버가 실제로 무효화한 범위를 맞춰야 한다.

11 / A DIFFERENT KIND OF PASS

JWT를 쓴다고 관계의 수명 문제가 없어지지는 않는다

모든 제품이 이 글의 보관함 방식만 사용하는 것은 아니다. JWT는 주장을 표현하는 토큰 형식이며, 서명된 형태나 암호화된 형태로 다룰 수 있다. 발급자, 대상, 만료 같은 클레임의 의미도 표준에 정의되어 있다. 서명된 토큰의 내용을 읽을 수 있다는 사실과 내용을 변조해도 유효하다는 주장은 다르며, 서명이 내용의 비밀성을 자동으로 주는 것도 아니다. [11]

함께보드가 서버 보관함을 매번 찾는 대신 서명된 정보를 검사하는 방식을 선택했다고 가정하자. 제품은 어떤 발급자의 어떤 대상 토큰을 인정할지, 언제 끝낼지, 권한이 바뀌면 어떻게 반영할지를 여전히 정해야 한다. 자료 구조의 이름이 바뀌어도 ‘이 요청에 누구의 어떤 관계를 인정할 것인가’라는 질문은 남는다.

특히 브라우저에서 토큰을 지우는 일만으로 이미 복사된 토큰의 유효성이 서버에서 자동으로 사라지는 것은 아니다. 즉시 종료를 요구하는 제품이라면 만료와 서버 측 상태 등 어떤 수단으로 종료를 확인할지 따로 설계해야 한다. 자격 증명을 담는 형식과 관계를 취소하는 정책은 같은 기능이 아니다.

따라서 작은 웹앱에 어떤 방식이 더 멋있어 보이는지를 먼저 물을 필요는 없다. 누가 정보를 보관하는지, 서버가 어떤 요청에서 무엇을 검사하는지, 관계를 종료해야 할 때 어디를 바꾸는지 적어 본다. 설명할 수 있는 약속과 검증 가능한 종료 절차가 있다면, 익숙한 쿠키와 서버 세션도 충분히 이해할 수 있는 구조가 된다.

12 / FOLLOWING ONE REQUEST

문제를 찾을 때는 이름 대신 요청의 근거를 따라간다

함께보드에서 로그인 후 문서가 열리지 않는다면 한 번의 요청을 골라 보자. 어느 주소의 로그인 응답이 쿠키를 설정하려 했는지, 브라우저가 어떤 조건으로 보관했는지, 문서 요청에 적용됐는지, 서버가 관계를 유효하게 찾았는지, 문서 권한까지 통과했는지 순서대로 확인한다. ‘로그인이 안 된다’는 말이 어느 경계에서 끊기는지 구체적으로 바뀐다.

이때 개발 도구의 화면을 공유하기 전에 쿠키 값과 인증 헤더를 가린다. 번호가 읽기 어려운 문자열이어도 누군가의 유효한 관계를 대표할 수 있다. 오류 설명에 필요한 것은 적용 조건, 전달 여부, 실패 단계이지 실제 비밀 값 전체가 아니다. 서버 로그에도 원인을 찾는 데 필요한 최소 정보를 남긴다.

검증에는 실패 상태를 함께 넣는다. 쿠키가 없는 요청, 이미 끝난 관계, 다른 사람의 문서, 보기 권한만 가진 사람의 수정 요청을 각각 확인한다. 정상 로그인으로 자기 문서가 열리는 한 가지 경우만 검사하면 허용하면 안 되는 길을 놓친다. 로그아웃 이후의 요청도 처음 로그인 전의 요청만큼 중요하다.

화면에는 사람이 취할 다음 행동을 표시한다. 관계가 끝났다면 다시 로그인하도록 안내하고, 로그인은 되어 있지만 권한이 없다면 접근 요청이나 목록으로 돌아갈 길을 제공할 수 있다. 내부 사유를 모두 공개하지 않더라도 사용자가 같은 비밀번호를 계속 입력하며 헛돌지 않도록 현재 상황을 정확하게 설명한다.

로그인 표시는 화면의 설명이고,
접근 허용은 서버가 매번 지켜야 할 약속이다.

1호사원의 메모

13 / REMEMBERING WITH CONDITIONS

서버가 기억한 것은 사람이 아니라 조건이 붙은 관계였다

처음의 지민 화면으로 돌아가자. 비밀번호 확인 뒤 함께보드는 로그인 관계를 만들었다. 브라우저는 그 관계를 찾는 번호를 쿠키로 보관했고, 다음 문서 요청에 조건이 맞는 쿠키를 전달했다. 서버는 유효한 관계를 찾아 계정을 확인하고, 그 계정이 해당 문서를 읽을 수 있는지 따로 판단했다. 이름이 화면에 보인다는 한 장면 뒤에는 이 여러 단계가 있었다.

관계는 영원한 기억이 아니다. 브라우저가 번호를 잃을 수 있고, 서버가 만료하거나 무효화할 수 있으며, 계정의 권한도 바뀔 수 있다. 브라우저에 남은 표시와 서버가 현재 인정하는 상태가 잠깐 다를 수 있다. 제품은 이 차이를 감추는 대신 다음 요청에서 정확히 판단하고 사람이 이해할 수 있는 회복 경로를 제공한다.

쿠키는 번호를 운반하고, 세션은 관계를 이어 주며, 권한 규칙은 어떤 일을 허용할지 정한다. HttpOnly와 Secure, 요청 의도를 다루는 방어는 각자의 경계를 보호한다. 어느 하나의 이름을 붙였다고 나머지 책임이 사라지지 않는다. 작은 서비스라도 각 도구가 어떤 질문에 답하는지 구분하면 구조를 설명하기 쉬워진다.

오늘의 메모는 이것이다. ‘서버가 나를 기억한다’는 말은 유효한 근거로 내 계정의 관계를 찾고, 지금 요청한 행동을 허용할지 다시 판단한다는 뜻이어야 한다. 로그인은 이름을 띄우는 기능에서 시작해, 다음 요청과 관계의 끝까지 이어지는 약속으로 완성된다.
