가상의 온라인 상점 ‘모눈상회’에는 주문이 천만 건 쌓여 있다. 상담원이 주문번호 7312를 입력하자 화면은 거의 즉시 한 건을 보여 줬다. 직원은 서버가 천만 줄을 눈으로 훑고도 이렇게 빨랐다고 생각했다. 하지만 데이터베이스가 실제로 한 일은 전부 읽기보다, 읽지 않아도 될 구역을 차례로 버리는 일이었다.

책에서 한 단어를 찾을 때 매 쪽의 첫 글자부터 검사하지 않는다. 뒤의 찾아보기에서 단어를 찾고 쪽 번호를 얻은 다음 원문으로 간다. 데이터베이스 인덱스도 비슷하지만 종이 색인보다 더 역동적이다. 행이 추가되고 바뀔 때 함께 갱신되고, 정렬된 키를 디스크 페이지에 나눠 담으며, 검색 조건과 현재 데이터 분포에 따라 아예 사용되지 않을 수도 있다.

이 글은 PostgreSQL의 B-tree와 보조 인덱스를 중심으로 설명하고 SQLite의 공식 문서로 공통 원리를 보완한다. 제품마다 테이블 저장 방식, 동시성 제어, 페이지 크기와 실행 계획이 다르므로 아래 그림의 키 개수와 단계 수를 실제 데이터베이스의 고정 규칙으로 읽으면 안 된다. 모눈상회는 설명을 위한 가상 사례이며 실제 성능 측정이 아니다. 기술 내용은 2026년 10월 5일 기준 공식 문서와 B-tree 원 논문을 확인했다.

01 / THE EXPENSIVE STRAIGHT LINE

천만 줄을 한 줄씩 읽는다면

인덱스가 없는 표에서 WHERE order_id = 7312를 실행한다고 상상하자. 데이터베이스는 각 페이지에서 행을 읽고 조건을 비교하는 순차 스캔을 선택할 수 있다. 원하는 행이 앞쪽에 있을 수도 있지만, 존재하지 않는 값을 확실히 확인하려면 마지막 구역까지 가야 한다. 행 수가 늘면 읽어야 할 후보도 함께 늘어난다.

순차 스캔이 나쁜 알고리즘이라는 뜻은 아니다. 아주 작은 표는 한두 페이지를 통째로 읽는 편이 인덱스 페이지를 거쳐 원본으로 다시 이동하는 것보다 싸다. 조건에 맞는 행이 대부분일 때도 어차피 원본 페이지를 넓게 읽어야 하므로 직선 경로가 유리할 수 있다. PostgreSQL 문서는 작은 시험 데이터에서 인덱스가 선택되지 않는 까닭을 페이지 단위 비용으로 설명한다.[7]

문제는 찾을 대상이 드문데도 매번 전체를 훑는 경우다. 천만 주문 중 한 주문, 수억 로그 중 한 요청 ID, 사원 명부 중 한 사번처럼 결과가 매우 좁다면 ‘어느 구역에 있는지’ 알려 주는 별도 구조가 읽기를 크게 줄인다. 그 구조가 인덱스다.

여기서 빠름의 핵심은 CPU가 천만 번 비교를 초고속으로 해냈다는 데 있지 않다. 애초에 대부분의 데이터 페이지를 요청하지 않았다는 데 있다. 저장장치와 메모리 사이를 오가는 페이지 수가 줄고, 캐시에 머물 가능성이 높은 작은 길잡이를 따라간다.

02 / A THIN MAP BESIDE THE TABLE

인덱스는 원본의 얇은 길잡이다

인덱스에는 보통 검색 키와 원본 행을 찾아갈 표지가 정렬돼 있다. 주문 표가 주문번호, 고객명, 주소, 결제 상태, 메모와 수십 열을 가진다면 주문번호 인덱스는 그 모든 내용을 복사할 필요가 없다. 주문번호와 원본 위치 같은 작은 항목을 모아 별도 구조로 둔다. 그래서 넓은 원본 표보다 같은 페이지에 훨씬 많은 키를 넣을 수 있다.

PostgreSQL의 인덱스는 테이블의 주 저장 영역인 heap과 따로 저장되는 보조 인덱스다. 일반적인 인덱스 스캔은 인덱스에서 조건에 맞는 항목을 찾은 뒤 heap의 해당 행을 다시 가져온다.[4] 인덱스가 답 그 자체라기보다 답이 있는 곳을 가리키는 지도라는 설명이 여기서는 정확하다.

지도가 얇아도 공짜는 아니다. CREATE INDEX를 실행하면 기존 행을 읽어 키 구조를 만들 공간과 시간이 필요하다. 이후 삽입·삭제·수정 때 원본과 인덱스가 함께 바뀌어야 한다. 조회가 빨라지는 대신 저장 공간과 쓰기 작업, 복구 기록과 캐시의 몫이 늘어난다.

또 인덱스는 ‘검색’이라는 이름 아래 모든 조건을 해결하지 않는다. 정렬 가능한 값의 동등·범위 비교, 단어 집합, 공간 겹침, 큰 표의 물리적 구역 요약은 서로 다른 문제다. PostgreSQL도 B-tree, Hash, GiST, SP-GiST, GIN, BRIN처럼 성질이 다른 인덱스 유형을 제공한다.[1]

03 / A TREE MADE OF PAGES

B-tree는 페이지 단위로 길을 줄인다

정렬된 키를 한 줄짜리 목록으로만 두면 중간 위치를 찾는 동안에도 큰 목록을 여러 페이지에서 읽어야 한다. B-tree는 키를 여러 갈래의 균형 잡힌 트리로 조직한다. 위쪽 페이지에는 값의 경계를 가르는 키와 아래쪽 페이지 표지가 있고, 가장 아래 잎 페이지에는 정렬된 실제 인덱스 항목이 있다.

B-tree를 소개한 Bayer와 McCreight의 논문은 고정 크기 페이지를 주기억장치와 보조 저장장치 사이에 전달되는 정보 블록으로 다뤘다. 페이지가 트리의 노드가 되고, 데이터가 늘거나 줄 때 트리도 성장하거나 수축한다.[10] 오늘의 구현은 훨씬 복잡하지만 ‘한 번의 저장장치 접근으로 많은 키와 자식 경계를 본다’는 출발점은 여전히 중요하다.

한 페이지에 자식 둘만 두는 이진 트리와 달리 데이터베이스의 B-tree 페이지는 많은 자식 방향을 품을 수 있다. 그러면 천만 키가 있어도 트리 높이는 비교적 낮게 유지된다. 루트 페이지는 자주 접근되어 메모리 캐시에 남기 쉽고, 탐색마다 전체 층을 디스크에서 새로 읽는다고 가정할 수도 없다.

‘B-tree는 정확히 세 번 읽으면 끝난다’ 같은 숫자는 위험하다. 키 크기, 페이지 크기, 채움 정도, 중복 값, 압축과 캐시 상태에 따라 높이와 실제 I/O가 달라진다. 중요한 것은 각 단계가 한 행씩 버리는 것이 아니라 값의 큰 구간을 통째로 제외한다는 점이다.

04 / ROOT, BRANCH, LEAF

루트에서 잎까지 몇 번만 내려간다

주문번호 7312를 찾는 단순한 모형을 보자. 루트 페이지의 경계가 3000, 6000, 9000이라면 7312는 6000과 9000 사이 자식으로 내려간다. 그 가지 페이지가 7000, 7600, 8300으로 다시 나뉜다면 7000과 7600 사이로 간다. 마지막 잎 페이지에서 정렬된 항목 중 7312를 찾고 원본 위치를 얻는다.

각 비교는 ‘정답인가’만 확인하지 않는다. 다음에 읽을 페이지를 정한다. 루트에서 첫 선택을 하는 순간 6000 미만과 9000 이상 구역은 후보에서 사라진다. 가지에서 다시 범위를 줄인다. 그래서 수많은 행을 가진 표에서도 소수의 인덱스 페이지와 필요한 원본 페이지만 만날 수 있다.

키가 존재하지 않아도 장점은 남는다. 7313이 잎 페이지의 7312와 7340 사이에 들어가야 하는데 항목이 없다면, 그 정렬 위치에서 ‘없음’을 판단한다. 전체 표 마지막 행까지 가서 없음을 증명할 필요가 없다. 존재 확인, 고유성 검사와 삽입 위치 결정에도 같은 정렬 구조가 쓰인다.

PostgreSQL은 기본 CREATE INDEX에 B-tree를 사용하며, B-tree는 정렬 가능한 값의 <, <=, =, >=, >와 그에 대응하는 범위 조건을 처리할 수 있다.[1] 빠른 동등 검색은 B-tree가 하는 일의 한 조각일 뿐이다.

05 / THE SECOND HOP

찾은 것은 행이 아니라 위치일 수 있다

잎에서 7312를 찾았다고 상담 화면에 고객 주소와 결제 메모가 이미 있는 것은 아니다. 주문번호 인덱스에 그 열들이 없다면 인덱스 항목이 가리키는 heap 위치로 두 번째 이동을 해야 한다. 이 이동은 흔히 테이블 조회, heap fetch, row lookup 같은 말로 설명된다.

문제는 서로 이웃한 인덱스 키가 원본에서도 이웃한다는 보장이 없다는 데 있다. 주문번호 순으로 인덱스 잎을 읽어도 원본 행은 여러 heap 페이지에 흩어져 있을 수 있다. 후보가 한두 건이면 부담이 작지만 수십만 건이면 임의 위치를 반복 방문하는 비용이 커진다. 이때 순차 스캔이 더 싼 선택으로 돌아올 수 있다.

동시성도 끼어든다. PostgreSQL의 다중 버전 동시성 제어에서는 같은 논리 행의 여러 버전 중 현재 질의의 스냅샷에 보이는 버전을 확인해야 한다. 인덱스 키를 찾았다는 사실만으로 그 행이 현재 트랜잭션에 보인다고 단정할 수 없다. 일반 인덱스 스캔이 heap을 확인하는 이유에는 값 가져오기뿐 아니라 가시성 확인도 있다.[4]

그래서 실행 계획의 ‘인덱스 사용’ 한 줄만 보고 모든 읽기가 끝났다고 생각하면 안 된다. 인덱스에서 몇 항목을 읽었는지, heap 페이지를 몇 번 방문했는지, 필터에서 후보를 얼마나 버렸는지까지 봐야 실제 경로가 보인다.

인덱스가 줄이는 것은 비교 횟수만이 아니다.

06 / FIND THE START, THEN WALK

범위와 정렬에도 같은 길을 쓴다

order_id BETWEEN 7000 AND 7999는 천 개 값을 각각 루트부터 다시 찾을 필요가 없다. B-tree로 7000이 시작되는 잎 위치를 찾고, 잎 페이지의 정렬된 항목을 오른쪽으로 이어 읽다가 7999를 넘으면 멈출 수 있다. 시작점 탐색과 연속 스캔을 결합하는 셈이다.

ORDER BY order_id LIMIT 20도 인덱스 정렬 순서와 맞으면 유리할 수 있다. 이미 정렬된 앞부분을 따라 스무 건만 얻고 멈출 수 있기 때문이다. 반대로 인덱스 순서와 다른 열로 정렬하면 후보를 모아 별도 정렬해야 할 수 있다. PostgreSQL 공식 문서도 B-tree가 결과를 정렬된 순서로 돌려주는 데 쓰일 수 있지만 언제나 순차 읽기와 정렬보다 빠른 것은 아니라고 설명한다.[1]

문자열의 접두 검색도 정렬된 시작 구간으로 바꿀 수 있으면 인덱스 후보가 된다. 그러나 LIKE '%phone%'처럼 앞부분이 열려 있으면 일반 B-tree가 어디서 시작해야 할지 알기 어렵다. 제품의 로캘과 연산자 클래스도 영향을 준다. ‘LIKE면 인덱스’ 또는 ‘LIKE면 전체 스캔’이라는 한 문장으로 고정할 수 없다.

정렬 구조는 찾기와 순서를 동시에 제공하지만, 질의가 요구한 순서와 인덱스가 저장한 순서가 맞아야 한다. 지름길은 방향이 맞을 때만 지름길이다.

07 / HAVING A ROAD IS NOT CHOOSING IT

인덱스가 있어도 안 쓰는 이유

데이터베이스는 질의를 받자마자 이름이 맞는 인덱스를 무조건 고르지 않는다. 가능한 실행 경로의 비용을 비교한다. 인덱스 루트와 잎을 읽고 heap의 흩어진 행을 다시 방문하는 비용, 테이블을 순서대로 읽는 비용, 정렬과 필터 비용을 추정해 상대적으로 싼 계획을 선택한다.

상태가 ‘배송 완료’인 주문이 전체의 92%라면 상태 인덱스로 92%의 위치를 얻은 뒤 원본을 찾아다니는 것은 비쌀 수 있다. 표의 대부분이 답이라면 처음부터 데이터 페이지를 순서대로 읽는 편이 낫다. 반대로 주문번호 한 건처럼 선택도가 높은 조건은 인덱스가 큰 구역을 제외한다.

PostgreSQL의 EXPLAIN 예제는 작은 표나 많은 행이 맞는 조건에서 플래너가 순차 스캔을 선택하는 모습을 보여 준다. EXPLAIN ANALYZE는 예상 행 수와 실제 행 수, 필터에서 제거된 행, 버퍼 접근과 실행 시간 같은 단서를 제공한다.[6] 인덱스가 존재한다는 사실보다 실행 계획이 무엇을 골랐는지가 중요하다.

함수로 열을 감싸거나 자료형을 암묵적으로 바꾸고, 인덱스 정렬 규칙과 맞지 않는 연산자를 쓰면 조건이 인덱스 검색으로 변환되지 않을 수도 있다. 이런 경우는 ‘데이터베이스가 바보라서 인덱스를 무시했다’가 아니라 준비된 길과 질의의 모양이 맞지 않는 문제다.

08 / ESTIMATING BEFORE READING

플래너는 통계로 후보 수를 짐작한다

계획을 고르는 시점에는 아직 실제 결과를 전부 읽지 않았다. 플래너는 행 수, 페이지 수, 서로 다른 값의 수, 자주 등장하는 값, 값의 분포 같은 통계로 조건이 몇 행을 돌려줄지 추정한다. 이 비율을 선택도라고 부른다. ‘한 건일 것’과 ‘구백만 건일 것’의 차이가 인덱스와 순차 스캔의 갈림길이 된다.

PostgreSQL의 통계는 ANALYZE나 VACUUM ANALYZE로 갱신되며, 최신이라도 표본에 기반한 근사치다. 행 수와 페이지 수도 매 순간 완벽히 갱신되는 값이 아니다.[5] 대량 삽입 뒤 통계가 오래됐거나 데이터 분포가 한쪽으로 심하게 치우치면 예상과 현실이 벌어질 수 있다.

서로 연관된 열을 독립적이라고 가정하면 오차가 더 커진다. 예를 들어 도시와 우편번호는 강하게 연결돼 있는데 각각의 선택도를 단순히 곱하면 후보 수를 지나치게 작게 볼 수 있다. 일부 데이터베이스는 다변량 통계로 이런 상관을 보완하지만, 모든 관계를 자동으로 이해하는 것은 아니다.

따라서 느린 질의를 볼 때는 ‘인덱스 하나 더’보다 예상 행과 실제 행의 차이를 먼저 확인하는 편이 좋다. 통계가 현실을 제대로 묘사하는지, 시험 데이터가 운영 데이터의 분포를 닮았는지 살펴야 한다. PostgreSQL 문서도 실제 워크로드와 실제에 가까운 데이터로 인덱스 사용을 검사하라고 권한다.[7]

09 / ORDER INSIDE THE KEY

복합 인덱스는 순서가 설계다

(shop_id, created_at) 복합 B-tree는 먼저 상점별로 묶고, 같은 상점 안에서 생성 시각 순으로 정렬한다고 생각할 수 있다. 특정 상점의 최근 주문을 찾는 질의는 두 열의 순서를 잘 활용한다. 상점 경계를 찾은 다음 그 안의 시각 범위를 이어 읽기 때문이다.

하지만 생성 시각만 조건에 있고 상점이 없다면 인덱스 전체에 흩어진 각 상점의 시각 구역을 만나야 한다. PostgreSQL 18은 특정 상황에서 선두 열의 가능한 값을 건너뛰며 반복 탐색하는 skip scan을 사용할 수 있지만, 그것이 모든 후행 열 질의를 자동으로 싸게 만드는 것은 아니다. 공식 문서는 다중 열 인덱스가 특히 선두 열 제약과 함께 효율적이며 무분별한 다중 열 인덱스를 피하라고 설명한다.[3]

SQLite의 공식 질의 계획 설명도 다중 열 인덱스에서 맨 왼쪽 열이 주 정렬 키이고 다음 열은 앞 열의 동률을 가르는 방식이라고 설명한다.[8] 구현 세부는 달라도 ‘열 집합만 같으면 순서는 상관없다’는 생각이 틀렸다는 점은 같다.

복합 인덱스를 설계할 때는 자주 쓰는 WHERE 조건, 범위가 시작되는 열, 정렬과 LIMIT, 값의 분포를 함께 본다. 인덱스 이름을 열 목록의 장식으로 보지 말고 질의가 실제로 따라갈 정렬 경로로 봐야 한다.

10 / WHEN THE MAP CONTAINS THE ANSWER

인덱스만 보고 끝날 수도 있다

질의에 필요한 열이 인덱스 안에 모두 있으면 원본 heap을 방문하지 않고 답을 만들 가능성이 생긴다. 이를 index-only scan이라 한다. 검색 키 외에 화면에 돌려줄 작은 열을 payload로 포함한 covering index를 만들기도 한다. 원본 위치로 튀는 두 번째 이동을 줄이는 것이 목적이다.

그러나 PostgreSQL에서는 값이 인덱스에 있다는 것만으로 충분하지 않다. 현재 MVCC 스냅샷에서 행이 보이는지 확인해야 하고, 그 가시성 정보는 인덱스 항목 자체에 없다. heap 페이지가 모든 트랜잭션에 보인다고 표시된 visibility map 비트가 켜져 있으면 heap 방문을 생략할 수 있지만, 최근 수정된 페이지라면 확인하러 가야 한다.[4]

covering index에 열을 많이 넣으면 읽기는 편해질 수 있지만 인덱스가 넓어진다. 한 페이지에 들어가는 항목이 줄고 트리와 캐시 비용이 커지며, 포함된 열이 바뀔 때 쓰기 부담도 생긴다. ‘원본을 한 번도 안 읽는다’는 멋진 문구만 보고 모든 열을 인덱스에 복제하면 얇은 지도라는 장점을 잃는다.

실행 계획에서 Index Only Scan이 보이더라도 heap fetch 수를 확인해야 한다. 물리적으로 가능한 계획과 실제로 원본 방문을 피한 정도는 다를 수 있다. PostgreSQL의 EXPLAIN 문서는 Heap Fetches와 버퍼 수를 함께 보여 주는 예를 제공한다.[6]

좋은 인덱스는 모든 열을 품지 않는다.

11 / READS BORROW FROM WRITES

읽기를 줄인 대가는 쓰기가 낸다

새 주문이 들어오면 테이블에 행 하나만 더하는 것으로 끝나지 않는다. 주문번호, 고객, 상태, 생성 시각에 각각 인덱스를 만들었다면 관련 인덱스에도 항목을 삽입해야 한다. 변경된 페이지는 복구 로그와 체크포인트, 복제에도 영향을 줄 수 있다. 인덱스가 많을수록 읽기 후보는 늘지만 쓰기 경로도 길어진다.

잎 페이지가 가득 차면 새 키를 넣을 공간을 만들기 위해 페이지가 나뉠 수 있다. 부모 페이지에 새 경계가 추가되고, 그 부모도 가득 찼다면 분할이 위로 이어질 수 있다. 반대로 삭제와 업데이트로 더 이상 유효하지 않은 항목을 정리하는 유지 작업도 필요하다. PostgreSQL의 B-tree 문서는 페이지 분할을 피하기 위한 삭제와 버전 churn 정리, 중복 키의 공간 절약 표현을 다룬다.[2]

값이 거의 매번 다른 고유 ID는 후보를 좁히기 좋다. 하지만 성별이나 완료 여부처럼 값 종류가 매우 적은 열은 단독 인덱스로 많은 행을 돌려줄 수 있다. 그렇다고 저카디널리티 인덱스가 항상 무가치한 것도 아니다. 특정 드문 값, 부분 인덱스, 다른 열과의 조합, 정렬과 covering 효과에 따라 달라진다.

결국 인덱스 설계는 저장 용량을 조회 시간으로 바꾸는 단순 거래가 아니다. 쓰기 지연, 잠금과 동시성, 캐시, 복구량, 유지 보수와 실제 질의 패턴이 모두 얽힌다. 사용하지 않는 인덱스는 공짜 보험이 아니라 계속 보험료를 내는 구조물이다.

12 / ONE SHAPE DOES NOT FIT EVERY QUESTION

모든 검색이 B-tree는 아니다

B-tree는 정렬할 수 있는 값의 동등 비교, 범위와 순서에 강하다. 그러나 문서 안의 여러 단어, 배열 요소, 지리 도형의 포함 관계, 엄청나게 큰 시계열 표의 물리적 구간을 찾는 문제는 다른 구조가 더 적합할 수 있다. PostgreSQL은 Hash를 단순 동등 비교에, GIN을 여러 구성 값을 품은 데이터에, GiST와 SP-GiST를 확장 가능한 탐색에, BRIN을 페이지 구간 요약에 사용할 수 있다.[1]

전문 인덱스는 만능 업그레이드가 아니다. 어떤 연산자를 지원하는지, 거짓 후보를 원본에서 다시 확인해야 하는지, 데이터가 물리적으로 얼마나 정렬돼 있는지, 업데이트가 얼마나 잦은지를 봐야 한다. 같은 ‘검색’ 버튼이어도 뒤의 조건은 정확 일치, 범위, 전문 검색, 최근접 이웃일 수 있다.

인덱스 여러 개를 결합하는 계획도 있다. PostgreSQL은 여러 인덱스 결과를 비트맵으로 합쳐 AND와 OR 조건을 처리할 수 있고, SQLite도 OR 조건에서 여러 인덱스 결과를 합치는 계획을 보여 준다.[9] 다만 하나의 적절한 복합 인덱스와 여러 단일 인덱스의 결합은 정렬 유지와 비용 특성이 다르다.

그래서 ‘인덱스를 걸었다’보다 ‘이 연산과 데이터 분포에 맞는 구조를 만들었다’가 정확한 표현이다. 데이터베이스는 인덱스 이름이 아니라 연산자, 순서, 통계와 비용을 보고 길을 고른다.

13 / FOLLOW THE PAGES

탐색 경로를 직접 따라가자

아래 체험은 실제 데이터베이스 엔진이 아니라 개념을 위한 작은 모형이다. 주문번호 한 건, 주문번호 범위, 대부분을 차지하는 상태 값, 복합 인덱스의 후행 열만 검색하는 네 상황을 골라 ‘다음 읽기’를 눌러 보자. 무엇을 읽고 무엇을 건너뛰는지가 단계마다 표시된다.

정확 검색은 루트, 가지, 잎, 원본 행으로 이동한다. 범위 검색은 시작 잎을 찾은 뒤 옆 잎을 이어 읽는다. 흔한 상태 값은 플래너가 순차 스캔을 고르는 예를 보여 준다. 복합 인덱스의 후행 열만 있는 조건은 준비된 정렬 경로를 곧장 타기 어려운 경우를 보여 준다.

단계 수와 키, 92%라는 비율은 모두 가상이다. 실제 결과를 재현하거나 PostgreSQL과 SQLite가 언제나 같은 계획을 고른다는 뜻이 아니다. 목적은 ‘인덱스 사용 여부’를 빠름의 배지로 보는 대신, 후보 수와 페이지 경로의 선택으로 읽는 것이다.

14 / ASK THE ENGINE WHAT IT CHOSE

실행 계획으로 실제 선택을 본다

직접 확인하려면 먼저 테스트용 표와 인덱스를 만들고 EXPLAIN으로 계획을 본다. PostgreSQL에서는 EXPLAIN (ANALYZE, BUFFERS) SELECT ...가 실제 실행과 버퍼 정보를 보여 준다. 단, ANALYZE 옵션은 질의를 실제로 실행하므로 UPDATE·DELETE·INSERT 앞에서는 트랜잭션과 롤백을 준비하지 않고 사용하면 데이터를 바꿀 수 있다.

관찰할 항목은 Seq Scan, Index Scan, Bitmap Heap Scan, Index Only Scan 같은 노드 이름만이 아니다. 예상 rows와 실제 rows가 얼마나 다른지, loops가 몇 번인지, 필터가 몇 행을 버렸는지, heap fetch와 buffers가 어떻게 나오는지 본다. 플래너의 추정이 틀렸는지, 경로는 맞지만 원본 방문이 많은지 분리할 수 있다.

SQLite에서는 EXPLAIN QUERY PLAN으로 SCAN과 SEARCH, USING INDEX, COVERING INDEX, 임시 B-tree 사용 여부를 볼 수 있다. 공식 문서는 출력 형식이 애플리케이션이 의존할 안정적 API가 아니며 릴리스에 따라 달라질 수 있다고 경고한다.[9] 사람이 진단하는 도구의 표시 문자열을 프로그램 로직으로 파싱하지 않는 편이 안전하다.

시험은 실제와 비슷한 행 수와 분포에서 해야 한다. 균등한 가짜 값 천 개로 만든 계획이 한 값에 90%가 몰린 운영 데이터의 계획을 대표하지 않는다. 먼저 통계를 갱신하고 같은 매개변수와 같은 자료형으로 확인한다. 계획을 억지로 고정하기 전에 왜 비용 추정이 그렇게 나왔는지 묻는다.

15 / THE ART OF NOT READING

인덱스는 지름길이 아니라 선택이다

모눈상회의 주문번호 7312가 빨리 나온 까닭은 서버가 천만 행을 믿기 어려운 속도로 전부 읽었기 때문이 아니다. 얇고 정렬된 인덱스의 루트와 가지가 큰 구간을 제외했고, 잎 항목이 원본 위치를 알려 줬기 때문이다. 검색의 성능은 얼마나 빨리 읽느냐보다 무엇을 읽지 않기로 했느냐에서 시작한다.

그러나 인덱스가 있으면 언제나 그 길을 쓰는 것은 아니다. 결과가 표의 대부분이라면 순차 스캔이 더 싸고, 통계가 오래되면 후보 수를 잘못 짐작할 수 있다. 복합 인덱스의 열 순서가 질의와 어긋나거나 필요한 값이 인덱스 밖에 있으면 추가 경로가 생긴다. 동시성 가시성 때문에 원본 확인을 피하지 못할 수도 있다.

인덱스를 늘리면 읽기 선택지는 많아지지만 삽입·수정·삭제가 관리할 구조도 많아진다. 페이지 분할과 정리, 저장 공간과 캐시의 비용을 낸다. 그래서 좋은 인덱스는 가능한 모든 열에 붙인 장식이 아니라, 반복되는 실제 질의가 불필요한 페이지를 건너뛰도록 설계한 경로다.

다음에 검색이 빠르거나 느릴 때 ‘인덱스가 있나’에서 멈추지 말자. 어떤 조건이 몇 행을 돌려주며, 플래너는 그 수를 어떻게 추정했고, 루트에서 잎과 원본까지 어떤 페이지를 방문했는지 물어보자. 데이터베이스는 답을 외우는 기계가 아니다. 매번 읽을 가치가 있는 곳과 건너뛸 곳을 계산하는 기계다.

빠른 데이터베이스는 모든 곳을 빨리 훑지 않는다.
