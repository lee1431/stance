가상의 출장비 신청 서비스 ‘한칸’에서 수진은 영수증 설명을 쓰다가 지급 규정을 확인하려고 링크를 눌렀다. 규정 페이지를 읽고 뒤로 가기를 눌렀더니 방금 쓰던 문장과 스크롤 위치가 그대로였다. 서버가 임시 글을 저장했다는 표시도 없었다. 브라우저는 무엇을 기억하고 있었을까.

많은 사람은 뒤로 가기를 “이전 URL을 다시 연다”라고 생각한다. 그러나 브라우저가 돌아가는 대상은 주소 문자열 하나가 아니라 탭 안에 쌓인 세션 방문 기록의 한 항목이다. 그 항목에는 URL뿐 아니라 문서와 연결된 상태, 스크롤 위치, 앱이 넣은 상태값, 브라우저가 보존하기로 한 사용자 상태가 붙을 수 있다. 어떤 경우에는 문서와 자바스크립트 메모리까지 통째로 잠들어 있다가 깨어난다.

한칸·수진·출장비 장면은 설명을 위해 만든 가상 사례이며 실제 서비스의 동작이나 측정 결과가 아니다. 기술 내용은 2026년 10월 4일 기준으로 WHATWG HTML 표준, W3C Navigation Timing, Chrome의 공식 개발 문서를 확인했다. 아래 체험은 방문 기록과 복원 정책을 단순화한 교육용 모형이며 실제 브라우저 기록을 읽거나 입력을 전송하지 않는다.

01 / A SENTENCE RETURNS

돌아왔더니 문장이 남아 있었다

수진이 규정 링크를 누를 때 브라우저는 현재 신청서 방문 뒤에 새 방문을 추가한다. 규정 화면이 활성 항목이 되고 신청서 항목은 한 걸음 뒤에 남는다. 뒤로 버튼은 이 목록에서 목표 걸음을 정한 뒤 그 항목을 다시 활성화한다. 단순히 주소창에 신청서 주소를 새로 입력하는 것과 출발점부터 다르다.

돌아오는 방법은 하나가 아니다. 브라우저가 신청서 문서를 메모리에 보관했다면 거의 그대로 다시 보여 줄 수 있다. 문서를 버렸어도 기록 항목의 URL로 새 문서를 만들고, 스크롤 위치나 폼 값을 별도로 복원할 수 있다. 보존할 자료가 없으면 네트워크나 HTTP 캐시에서 자원을 얻어 처음부터 실행할 수도 있다. 사용자가 보는 “뒤로” 한 번 뒤에는 여러 경로가 숨어 있다.

WHATWG HTML 표준은 세션 방문 기록 항목에 URL, 문서 상태, History API 상태, 스크롤 복원 모드와 위치, 구현이 정하는 사용자 상태를 둔다.[1] 브라우저는 폼 컨트롤 값 같은 것을 사용자 상태로 보존할 수 있다. 따라서 입력이 남았다는 관찰 하나만으로 서버 자동 저장이나 BFCache 사용을 단정할 수 없다.

02 / THE STACK OF VISITS

브라우저는 방문을 항목으로 쌓는다

한 탭에서 신청서 → 규정 → 도움말을 차례로 열었다면 현재 위치는 세 번째 항목이다. 뒤로 한 번은 규정, 두 번은 신청서를 목표로 한다. 규정으로 돌아온 뒤 새 링크를 열면 그 앞에 있던 도움말 방향의 기록은 보통 잘리고 새 갈래가 생긴다. 종이책의 페이지 번호보다는 되돌리기 기록에 가깝다.

이 목록은 단순한 URL 배열도 아니다. 같은 주소가 여러 번 나타날 수 있고, 한 문서 안에서 조각 식별자나 History API 상태만 바뀐 항목도 끼어든다. iframe 같은 자식 탐색 영역의 이동도 사용자가 보는 하나의 뒤로·앞으로 인터페이스에 맞춰 조정되어야 한다. HTML 표준이 이 영역을 복잡한 부분이라고 경고하는 이유다.[1]

history.length는 현재 탭이 접근하는 전체 세션 방문 기록 항목 수를 알려 주지만, 보안과 사용자 경험 때문에 모든 항목의 URL 목록을 페이지에 내주지는 않는다. 웹페이지는 사용자가 다른 사이트에서 어디를 거쳐 왔는지 마음대로 훑을 수 없다. 앱이 아는 것은 현재 상태와 자신이 추가한 상태, 그리고 탐색 때 전달되는 제한된 신호다.

브라우저 UI의 뒤로 버튼과 자바스크립트의 history.back()은 모두 한 단계 뒤 항목으로 이동하도록 요청한다. 이전 항목이 없으면 아무 일도 하지 않는다. 이 동작은 “이전 URL에 GET 요청을 보내라”가 아니라 “전체 방문 기록에서 한 단계 전을 활성화하라”로 정의된다.[2]

03 / SAME ADDRESS, DIFFERENT VISIT

같은 URL은 같은 방문이 아니다

신청서 주소가 /expense/42라고 하자. 수진이 주소창에 이 주소를 다시 입력하면 새 탐색이 시작되고 보통 새 방문 항목과 새 문서가 만들어진다. 현재 페이지에서 새로고침하면 현재 항목을 다시 불러오는 탐색이 일어나며, 항목을 하나 더 뒤에 추가하는 것과는 다르다. 규정 페이지에서 뒤로 돌아오면 과거에 만들어 둔 신청서 항목을 순회한다.

세 동작의 화면 주소는 모두 같아질 수 있다. 그러나 “어떤 방문 항목을 활성화했나”, “기존 문서를 되살렸나”, “새 문서를 만들었나”, “브라우저가 어떤 사용자 상태를 복원했나”가 다르다. URL은 자원의 이름이지 탭의 전체 시간선과 메모리 상태를 표현하는 일련번호가 아니다.

W3C Navigation Timing은 일반 탐색, 새로고침, 뒤로·앞으로 계열을 서로 다른 탐색 유형으로 구분한다.[5] 개발자는 performance.getEntriesByType('navigation')[0].type을 관찰해 새 문서를 만든 탐색이 navigate, reload, back_forward 가운데 무엇인지 볼 수 있다. 다만 BFCache에서 문서 자체가 복원되면 새 Navigation Timing 항목이 생기는 문제만으로 판정할 수 없으므로 pageshow 신호도 함께 본다.

04 / ENTRY IS NOT DOCUMENT

항목과 문서는 한 몸이 아니다

방문 기록 항목은 그때의 URL과 상태를 가리키는 자리이고, 문서는 HTML을 파싱해 만든 DOM과 실행 환경이다. 항목이 남아 있어도 연결된 문서가 메모리에서 제거될 수 있다. 메모리가 부족하거나 브라우저 정책상 보관할 수 없으면, 나중에 그 항목으로 돌아올 때 저장된 URL을 사용해 새 문서를 채운다.

반대로 하나의 문서가 여러 방문 항목을 만들 수도 있다. 단일 페이지 앱에서 pushState()로 필터나 상세 보기 상태를 기록하면 네트워크로 새 HTML을 받지 않고도 목록에 항목이 추가된다. 뒤로 갈 때 같은 Document 안에서 상태를 바꾸는 “같은 문서 탐색”이 일어난다.

이 구분은 오류를 찾을 때 중요하다. 초기화 코드가 다시 실행되지 않았는데 화면이 옛 상태로 돌아왔다면 기존 문서 복원일 수 있다. load가 다시 발생하고 모든 모듈이 초기화됐다면 새 문서를 만든 경로일 가능성이 크다. 그러나 브라우저와 상황에 따라 경로가 바뀌므로 앱은 어느 한쪽만 일어난다고 가정해서는 안 된다.

HTML 표준도 기록을 순회할 때 항목의 문서가 없으면 저장된 URL과 문서 상태를 이용해 새 Document를 채우는 절차를 둔다.[1] “기록이 남는다”와 “프로세스 메모리에 문서가 남는다”는 별개의 약속이다.

뒤로 버튼은 지나온 순간을 가리킨다.

05 / FREEZE THE WHOLE PAGE

문서 전체를 잠시 얼린다

뒤로·앞으로 캐시, 줄여서 BFCache는 다른 페이지로 떠날 때 현재 문서 전체를 메모리에 보관했다가 기록 순회 때 되살리는 최적화다. HTTP 캐시가 응답 바이트를 저장하는 것과 다르다. BFCache에는 DOM, 자바스크립트 힙, 화면 상태 같은 살아 있는 페이지가 함께 보존될 수 있다.[3]

그래서 복원이 빠르다. HTML을 다시 내려받아 파싱하고 스타일과 스크립트를 실행해 같은 화면을 재구성하는 대신 멈춰 둔 문서를 다시 활성화한다. 수진이 입력한 문장이 DOM의 input 값으로 남아 있었다면 그것도 함께 돌아온다. 스크롤 위치와 펼친 메뉴, 메모리 안의 변수까지 출발 직전 모습에 가까울 수 있다.

그러나 “캐시”라는 말 때문에 디스크의 HTTP 캐시와 섞어 생각하면 안 된다. HTTP 응답에 max-age가 남아 있는지는 자원을 재사용할 때의 문제다. BFCache 적중은 네트워크 요청 자체 없이 기존 문서를 복원할 수 있다. 반대로 BFCache가 실패해도 HTTP 캐시 덕분에 재구성이 빠를 수 있다. 체감 속도만으로 어느 층이 일했는지 판정하기 어렵다.

문서가 BFCache에 들어가 있는 동안 브라우저는 타이머와 대부분의 보류 작업을 멈춘다. 다시 활성화되면 처리가 이어질 수 있다.[3] 떠난 동안 현실의 시간과 서버 상태는 진행됐는데 페이지의 실행은 멈춰 있었으므로, 복원 직후에는 “그대로 이어서”와 “현재 상태 재검사”를 구분해야 한다.

06 / WHAT EXACTLY SURVIVED

입력값이 남았다고 BFCache는 아니다

브라우저는 BFCache가 없어도 방문 기록 항목에 구현이 정하는 사용자 상태를 붙일 수 있다. HTML 표준은 폼 컨트롤 값이 그 예가 될 수 있다고 적는다.[1] 스크롤 위치도 항목의 복원 데이터다. 새 문서를 만든 뒤 이 값을 다시 놓으면 사용자는 페이지 전체가 살아 돌아왔다고 느낄 수 있다.

반대로 모든 값이 반드시 돌아온다고 기대해서도 안 된다. 비밀번호 필드, 자동완성 정책, 동적으로 만든 컨트롤, 브라우저별 구현, 메모리 압박과 개인정보 보호 모드에 따라 결과가 달라질 수 있다. 사용자의 중요한 초안은 브라우저가 우연히 보존해 줄 상태가 아니라 앱이 명시적으로 저장할 데이터다.

초안을 서버나 IndexedDB, localStorage 등에 저장하는 일도 목적이 서로 다르다. 서버 저장은 기기 간 복구와 협업을 가능하게 하지만 인증과 충돌 처리가 필요하다. 로컬 저장은 오프라인 복구에 유용하지만 다른 기기에는 없다. BFCache는 빠른 탐색 최적화일 뿐 장기 저장소나 업무 기록이 아니다.

“뒤로 갔더니 남아 있었으니 저장됐다”는 위험한 결론이다. BFCache에 있던 값은 탭 종료나 메모리 회수로 사라질 수 있고, 폼 복원 값도 브라우저의 장기 보존 약속이 아니다. 저장 완료는 별도 영속화 결과로 판단해야 하며, 화면이 기억하는 것과 데이터가 보존된 것을 분리해 알려야 한다.

07 / ONE DOCUMENT, MANY STEPS

주소만 바뀌는 페이지도 기록을 만든다

단일 페이지 앱은 상품 목록에서 상세 화면으로 바뀔 때 새 HTML 문서를 열지 않을 수 있다. 자바스크립트가 DOM을 바꾸고 history.pushState(data, '', url)를 호출하면 현재 문서에 새 방문 기록 항목이 추가된다. HTML 표준은 전달한 데이터를 직렬화해 항목의 상태로 저장하고 선택한 URL을 기록하도록 정의한다.[2]

사용자가 뒤로 가면 브라우저는 이전 항목의 URL과 state를 활성화하고 페이지는 popstate를 받아 화면을 이전 상태로 맞춘다. pushState()를 호출한 순간에는 popstate가 발생하지 않는다. 앱이 새 상태를 만든 직후의 렌더링은 앱 자신이 하고, 나중에 기록을 순회할 때 복원을 처리한다.

replaceState()는 현재 항목의 상태와 URL을 바꾸며 새 걸음을 추가하지 않는다. 검색 필터의 기본값을 정리하거나 잘못된 상태를 교정할 때 유용하지만, 사용자가 뒤로 갔을 때 만나야 할 의미 있는 화면까지 계속 덮어쓰면 뒤로 버튼이 기대와 다르게 멀리 이동한다.

SPA 내부의 같은 문서 탐색과, 다른 사이트로 갔다가 SPA 전체 문서를 BFCache로 복원하는 일은 별개다. 전자는 앱이 한 문서 안에 기록 항목을 만드는 방식이고, 후자는 브라우저가 문서 전체를 보관하는 최적화다. 같은 뒤로 버튼에서 만나지만 책임의 경계가 다르다.

08 / LOAD IS NOT RETURN

복원은 load와 다른 신호를 보낸다

처음 문서를 불러오면 load가 일어난 뒤 pageshow가 발생한다. BFCache에서 복원될 때는 새 문서를 로드하지 않으므로 load를 다시 기대할 수 없지만 pageshow는 발생한다. 이때 PageTransitionEvent.persisted가 참이면 BFCache 복원을 뜻한다.[3]

떠나는 쪽에서는 pagehide를 관찰할 수 있다. 그 이벤트의 persisted가 참이면 브라우저가 문서를 BFCache에 넣으려는 의도를 보이지만, 이후 메모리 압박 등으로 제거될 수 있어 실제 복귀를 보장하지는 않는다. 최종 복원 여부는 돌아왔을 때의 pageshow.persisted로 확인한다.

unload는 페이지가 반드시 파괴된다는 옛 가정과 충돌한다. Chrome의 공식 지침은 이 이벤트를 쓰지 말고 pagehide를 사용하라고 권한다. 데스크톱의 일부 브라우저에서는 unload 리스너가 BFCache 자격을 막으며, 모바일에서는 이벤트 자체가 신뢰할 수 없을 수 있다.[3]

앱의 초기화가 load에만 묶여 있으면 복원 때 필요한 갱신을 놓친다. 반대로 pageshow에서 모든 초기화를 무조건 반복하면 이미 연결된 이벤트 리스너나 컴포넌트를 중복 생성할 수 있다. 새 문서 시작과 기존 문서 복원을 구분하고, 복원 때 필요한 검증만 멱등하게 실행해야 한다.

빠르게 돌아온 화면은
현재의 화면이라는 뜻이 아니다.

09 / THE WORLD MOVED ON

빠른 복원은 낡은 화면도 되살린다

수진이 규정을 읽는 동안 다른 탭에서 로그아웃했거나 출장비 한도가 바뀌었다고 하자. BFCache는 떠날 때의 신청서 문서를 거의 그대로 복원하므로, 화면에는 예전 사용자 이름과 한도가 잠깐 또는 계속 보일 수 있다. 이것은 서버가 과거로 돌아간 것이 아니라 멈춰 있던 클라이언트 문서가 깨어난 결과다.

Chrome의 BFCache 안내는 공용 컴퓨터에서 로그아웃한 뒤 다음 사람이 뒤로 갔을 때 사적인 정보가 보일 위험을 예로 들며, pageshow에서 persisted가 참이면 필요한 상태를 갱신하라고 권한다.[3] 민감한 화면은 복원 직후 세션 유효성을 확인하고, 무효하면 내용을 감추거나 로그인 화면으로 전환해야 한다.

그렇다고 모든 복원마다 전체 페이지를 강제 새로고침하면 BFCache의 속도와 입력 보존 이점을 버린다. 서버가 바뀔 수 있는 작은 데이터만 다시 확인하거나, 마지막 확인 시각과 현재 시각을 비교해 일정 시간이 지난 경우에만 갱신할 수 있다. 사용자 초안처럼 로컬에서 이어야 할 상태와 권한·잔액처럼 서버가 진실인 상태를 나눈다.

Cache-Control: no-cache가 붙어 있어도 BFCache 복원은 HTTP 캐시 재검증 절차가 아니므로 화면을 보여 주기 전에 서버에 묻지 않을 수 있다. 공식 안내는 시시각각 바뀌는 내용이라면 pageshow에서 업데이트를 가져오라고 설명한다.[3] HTTP 캐시 지시문 하나가 모든 종류의 복원을 통제한다고 생각하면 빈틈이 생긴다.

10 / NOT EVERY PAGE CAN SLEEP

항상 얼려 둘 수는 없다

브라우저는 모든 문서를 무기한 BFCache에 둘 수 없다. 기기 메모리가 부족하면 보관 중인 문서를 제거할 수 있고, 특정 API 사용이나 진행 중인 작업, 프레임 구조, 브라우저 정책 때문에 처음부터 자격이 없을 수 있다. 사용자가 브라우저를 종료하거나 탭을 복제하고 복원하는 상황도 단순한 BFCache 복귀와 다르다.

그래서 제품 코드는 BFCache 적중을 성능 향상으로 받아들이되 정확성의 전제로 두면 안 된다. 적중하면 기존 문서를 안전하게 깨우고, 실패하면 새 문서가 서버·로컬 저장소에서 필요한 상태를 재구성해야 한다. 어느 길에서도 제출 중복, 초안 손실, 권한 노출이 없어야 한다.

Chrome 123부터 제공된 PerformanceNavigationTiming.notRestoredReasons는 기록 탐색에서 BFCache를 사용하지 못한 이유를 프레임 구조와 함께 보고할 수 있다.[6] 다만 값이 null이라는 사실만으로 BFCache 적중을 뜻하지는 않는다. 실제 복원 판정에는 pageshow.persisted를 사용하고, 이 API는 실패 원인을 진단하는 보조 자료로 본다.

브라우저 구현은 계속 바뀐다. 어떤 기능이 영원히 차단 사유라고 하드코딩하기보다 현재 개발자 도구와 notRestoredReasons를 확인한다. Chrome DevTools의 Application 패널에는 Back/forward cache 테스트가 있어 페이지를 떠났다 돌아오게 한 뒤 복원 여부와 실패 이유를 보여 준다.[8]

11 / TRY THE THREE RETURNS

세 가지 돌아오기를 비교하자

아래 모형에는 신청서 항목과 규정 항목이 있다. 초안을 바꾸고 규정으로 이동한 뒤, 돌아오는 방식을 고른다. “BFCache 복원”은 기존 문서와 메모리 초안을 그대로 되살린다. “기록 상태로 재구성”은 새 문서를 만들되 브라우저가 보존한 폼 값을 놓는다. “새 주소 방문”은 같은 URL의 새 방문이라 빈 초기 화면에서 시작한다.

이 모형은 실제 브라우저의 모든 정책을 재현하지 않는다. BFCache 사용 여부도 실제 네트워크도 측정하지 않는다. 목적은 같은 주소와 비슷한 화면이 서로 다른 경로로 만들어질 수 있음을 눈으로 비교하는 것이다.

12 / LOOK INSIDE THE TAB

직접 확인하는 방법

작은 테스트 페이지에서 load, pagehide, pageshow, popstate 로그를 남겨 보자. 다른 페이지로 이동했다가 브라우저 뒤로 버튼으로 돌아온다. pageshow의 persisted가 참이면 BFCache 복원이다. 거짓이고 Navigation Timing의 type이 back_forward라면 기록 순회로 새 문서를 만든 경우를 관찰한 것이다.

개발자 도구의 Network 패널만으로는 충분하지 않을 수 있다. BFCache 적중 때 문서 요청이 없다는 점은 볼 수 있지만, 확장 프로그램이나 개발자 도구 자체가 페이지 동작과 자격에 영향을 줄 수도 있다. Chrome의 전용 Back/forward cache 테스트와 이벤트 로그를 함께 사용하고 실제 사용자 환경의 차이도 염두에 둔다.

입력값이 남는지만 보지 말고 자바스크립트 메모리의 임시 카운터, DOM으로 만든 요소, 스크롤 위치를 각각 관찰해 보자. BFCache 복원이라면 기존 문서의 값이 함께 돌아오는 경향이 있고, 새 문서 재구성이라면 초기화 코드가 다시 실행된 뒤 브라우저 또는 앱의 저장 값만 돌아온다.

performance.getEntriesByType('navigation')[0].notRestoredReasons가 지원되면 콘솔에서 확인할 수 있다. 보안상 교차 출처 iframe의 자세한 내부 정보는 제한될 수 있다.[6] 원인을 제거한 뒤 전용 테스트를 다시 실행해 개선 여부를 검증한다.

13 / DESIGN FOR RESTORATION

앱은 복원을 전제로 설계한다

첫째, 중요한 초안은 명시적으로 저장한다. 자동 저장 상태를 “저장 중”, “이 기기에 저장됨”, “서버에 저장됨”처럼 실제 내구성에 맞춰 표시한다. BFCache나 브라우저 폼 복원을 저장 완료 표시로 사용하지 않는다. 새 문서 경로에서도 같은 초안을 되찾을 수 있어야 한다.

둘째, 복원 때 서버가 진실인 값을 재검사한다. 세션·권한·재고·잔액·마감 시각처럼 떠난 동안 바뀔 수 있는 값은 pageshow에서 선택적으로 갱신한다. 화면을 먼저 보여 주면 안 되는 민감한 정보는 확인 전 가림 상태를 사용한다. 갱신 요청이 실패했을 때 옛 값을 현재 값처럼 확정해서 보여 주지 않는다.

셋째, 페이지를 떠날 때의 정리는 unload 완료에 의존하지 않는다. 서버에 꼭 남아야 하는 작업은 그 전에 확정하고, 열린 연결이나 다른 탭을 막을 수 있는 자원은 pagehide 같은 생명주기 신호에서 정리한다. 미저장 경고가 정말 필요할 때만 beforeunload를 조건부로 붙이고 저장이 끝나면 제거한다.[3]

넷째, 분석에서도 복원을 센다. BFCache 복원은 새 load가 없으므로 load 기반 페이지뷰만 보면 실제 화면 노출을 빠뜨릴 수 있다. 공식 안내는 pageshow.persisted를 사용해 복원을 별도로 측정하라고 설명한다.[3] 단, 사용자의 뒤로·앞으로 행동을 무조건 새 세션이나 새 의도로 해석하지는 않는다.

마지막으로 뒤로 버튼을 앱 안에서 가로채 도망가지 못하게 만드는 장치로 쓰지 않는다. 기록을 의미 없이 여러 번 추가하거나 되돌아오자마자 다시 밀어내면 사용자의 기본 탐색 모델을 깨뜨린다. pushState는 사용자가 다시 찾을 가치가 있는 화면 상태에, replaceState는 현재 항목을 교정할 때 쓴다.

14 / AN INTERFACE TO TIME

뒤로 버튼은 시간의 인터페이스다

수진이 신청서로 돌아왔을 때 남아 있던 문장은 한 가지 원인으로 설명되지 않는다. 문서 전체가 BFCache에서 깨어났을 수도 있고, 새 문서에 브라우저가 보존한 폼 값이 놓였을 수도 있고, 앱의 초안 저장소가 값을 복원했을 수도 있다. 보이는 결과가 같아도 신뢰할 수 있는 지속 시간과 실패 조건은 다르다.

브라우저는 방문 기록 항목을 시간선으로 관리한다. 항목은 URL보다 넓고, 문서는 항목과 항상 함께 살아 있지 않으며, BFCache는 그 문서를 잠시 얼려 빠르게 되살리는 선택적 최적화다. 같은 문서 안에서도 History API가 새 걸음을 만들 수 있다. 뒤로 가기는 이 여러 층을 하나의 익숙한 화살표로 감춘다.

좋은 웹앱은 그 화살표를 예외 상황으로 취급하지 않는다. 기존 문서가 깨어나도, 새 문서가 재구성돼도, 중요한 데이터는 잃지 않고 민감한 정보는 낡은 채 드러내지 않는다. 복원 신호를 관찰하고 최신성과 연속성의 경계를 분리한다.

다음에 뒤로 갔는데 화면이 즉시 살아난다면 “캐시가 됐나 보다”에서 한 걸음 더 가 보자. 어느 방문 항목으로 돌아왔는가, 문서가 살아 있었는가, 어떤 상태가 브라우저와 앱에서 복원됐는가. 뒤로 버튼은 과거 주소로 가는 문이 아니라, 탭이 기억한 과거 상태와 현재 세계를 다시 맞추는 인터페이스다.

복원은 과거를 되살리는 기술이고,
갱신은 현재와 다시 만나는 기술이다.
