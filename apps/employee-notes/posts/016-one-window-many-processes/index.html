ISSUE 16 / ONE WINDOW, MANY PROCESSES

창 하나 열었는데,
왜 프로세스가 여러 개지?

작업 관리자에 늘어선 브라우저 프로세스는 같은 일을 복제한 낭비가 아니다. 믿을 수 없는 웹 콘텐츠와 강한 권한, 서로 다른 사이트와 그래픽 작업을 경계로 나눠 놓은 구조다. 탭 뒤의 작은 운영체제를 따라간다.

가상의 사무실 ‘모눈’에서 직원이 브라우저 창 하나와 탭 세 개만 열었다. 그런데 운영체제 작업 관리자는 같은 브라우저 이름을 단 프로세스를 열두 개 보여 줬다. 직원은 창이 하나인데 왜 프로그램을 열두 번 실행했느냐고 물었다. 메모리가 모자란 까닭도 저 숫자 때문처럼 보였다.

겉으로는 하나의 브라우저지만 그 안에서 다루는 대상은 서로 믿을 수 없다. 주소창과 비밀번호 저장소는 강한 권한을 가진다. 방금 방문한 웹사이트의 JavaScript는 인터넷에서 내려온 낯선 코드다. 다른 회사의 사이트 둘이 한 화면의 iframe으로 섞일 수도 있고, GPU 드라이버와 네트워크 스택은 복잡한 입력을 처리한다. 이 모든 일을 같은 주소 공간과 같은 권한에 넣으면 한 부분의 오류나 침해가 전체를 건드릴 수 있다.

Chromium 계열 브라우저는 일을 여러 운영체제 프로세스로 나눠 이런 경계를 만든다. 이 글의 ‘브라우저’는 주로 Chromium의 데스크톱 구조를 가리킨다. 모바일, 다른 브라우저, 운영체제, 설정과 메모리 상황에 따라 실제 배치는 달라진다. 모눈 사무실은 설명을 위한 가상 사례이며 실제 측정이나 장애 기록이 아니다. 기술 내용은 2026년 10월 5일 기준 Chromium과 Chrome의 공식 문서를 확인했다.

01 / A LONG LIST BEHIND ONE WINDOW

창은 하나인데 목록은 길다

브라우저 창은 사용자를 위한 묶음이다. 탭, 주소창, 뒤로 가기, 다운로드와 설정이 한 외형 안에 모인다. 운영체제의 프로세스는 다른 기준으로 나뉜다. 독립된 주소 공간, 권한, 오류 경계와 자원 회계 단위가 필요할 때 별도 프로세스가 생긴다. 화면에 보이는 창의 수와 보이지 않는 실행 경계의 수가 같아야 할 이유는 없다.

Chromium의 멀티프로세스 설계 문서는 주 브라우저 프로세스가 사용자 인터페이스와 자식 프로세스를 관리하고, 렌더러 프로세스가 웹 콘텐츠를 실행한다고 설명한다. 여러 프로세스를 쓰면 렌더링 엔진의 오류가 브라우저 전체로 번지는 것을 줄이고, 렌더러가 다른 프로세스와 시스템에 접근하는 범위를 제한할 수 있다.[1]

따라서 작업 관리자에서 같은 실행 파일 이름이 여러 줄 보인다는 사실만으로 중복 실행이나 악성 동작을 뜻하지 않는다. 같은 브라우저 제품이 역할이 다른 프로세스를 여러 개 띄운 결과일 수 있다. 반대로 ‘프로세스가 많으니 무조건 안전하다’고 결론 내려서도 안 된다. 분리는 보안 정책과 통신 검증이 함께 있을 때 경계가 된다.

첫 질문은 “왜 열두 개나 낭비하지?”보다 “어떤 권한과 실패를 서로 떼어 놓으려고 열두 경계를 만들었지?”가 낫다. 숫자는 결과이고, 구조의 목적은 믿음의 정도가 다른 일을 같은 방에 두지 않는 것이다.

02 / ROOMS AND WORKERS

프로세스와 스레드는 무엇이 다른가

프로세스를 건물 안의 잠긴 작업실로, 스레드를 그 방 안에서 일하는 작업자로 비유할 수 있다. 한 프로세스의 스레드들은 보통 같은 메모리 공간을 공유하므로 자료를 빠르게 주고받는다. 대신 잘못된 메모리 접근은 같은 방의 다른 작업까지 손상시킬 수 있다. 다른 프로세스는 기본적으로 주소 공간이 갈려 있어 직접 같은 포인터를 사용할 수 없다.

프로세스 사이에는 운영체제가 중재하는 프로세스 간 통신, 즉 IPC가 필요하다. Chromium은 브라우저와 렌더러, 서비스들이 메시지를 주고받는 구조를 사용한다.[2] 복사, 직렬화, 검증, 스케줄링이 끼므로 같은 함수 안에서 메모리를 읽는 것보다 복잡하다. 경계를 얻는 대신 통신 비용과 설계 부담을 낸다.

스레드는 프로세스보다 ‘가벼운 프로세스’라는 한 문장으로 끝낼 수 없다. 렌더러 프로세스 하나 안에도 JavaScript와 DOM을 다루는 주 스레드, 합성 스레드, 래스터 작업자 등이 협력한다. 한 프로세스라는 사실은 한 번에 하나의 일만 한다는 뜻이 아니다. 반대로 스레드가 많아도 주소 공간과 권한이 하나라면 프로세스 분리와 같은 보안 경계가 되지 않는다.

브라우저의 설계자는 빠른 공유가 필요한 일은 같은 프로세스의 스레드로 묶고, 충돌·권한·신뢰 수준을 갈라야 하는 일은 프로세스로 떼어 낸다. 어디에 선을 긋느냐가 성능과 안정성, 보안의 타협점이다.

03 / THE COORDINATOR

브라우저 프로세스는 조정자다

브라우저 프로세스는 주소창, 탭 띠, 뒤로 가기 같은 ‘웹페이지 바깥’의 인터페이스를 다룬다. 어떤 URL로 이동할지 판단하고, 렌더러를 만들거나 재사용하며, 파일 선택과 권한 요청처럼 웹 콘텐츠가 직접 가져서는 안 되는 능력을 중재한다. 자식 프로세스가 요청한 일이 정책상 허용되는지 검사하는 위치이기도 하다.

Chrome for Developers의 브라우저 구조 설명은 브라우저 프로세스가 애플리케이션의 Chrome UI와 파일 접근 같은 권한 있는 부분을 제어하고, 렌더러가 탭 안의 웹사이트를 담당한다고 구분한다.[3] 이는 웹페이지가 주소창 모양을 마음대로 바꾸거나 사용자의 모든 파일을 직접 읽을 수 없게 만드는 구조적 분리다.

그렇다고 브라우저 프로세스가 모든 바이트를 혼자 처리하는 왕이라는 뜻은 아니다. 일을 전문 서비스와 렌더러에 나누고, 결과를 모아 사용자에게 하나의 제품처럼 보이게 하는 조정자에 가깝다. 권한이 강한 만큼 이 프로세스의 입력 검증과 생명주기 관리는 중요하다. 렌더러가 보낸 메시지를 단순히 믿어 버리면 분리의 효과가 약해진다.

주소 입력부터 새 문서가 보이기까지 브라우저 프로세스는 현재 탭의 문맥, 탐색 대상의 사이트, 기존 프로세스의 상태와 보안 정책을 보고 렌더러 배치를 결정한다. ‘탭 하나를 열었으니 프로세스 하나 추가’ 같은 단순 계산이 아닌 까닭이 여기서 시작된다.

04 / THE ROOM THAT RUNS THE WEB

렌더러는 웹을 실행하는 방이다

렌더러 프로세스는 HTML을 문서 구조로 만들고 CSS를 적용하며 JavaScript를 실행한다. 레이아웃과 페인트 정보를 만들고 입력 이벤트를 웹페이지 코드에 전달한다. 우리가 ‘페이지가 움직인다’고 느끼는 많은 일이 이 방에서 일어난다. 인터넷에서 받은 복잡하고 때로는 악의적인 입력을 처리하는 곳이므로 강한 권한을 그대로 주지 않는다.

렌더러가 파일을 저장하거나 장치에 접근해야 하면 보통 브라우저가 제공하는 인터페이스를 통해 요청한다. 브라우저 프로세스는 사용자의 선택과 권한 정책을 확인한 뒤 허용된 동작만 대신 수행한다. 샌드박스 안의 코드가 운영체제 기능을 마음대로 부르는 구조와 다르다.

하나의 렌더러에는 하나 이상의 문서나 워커가 들어갈 수 있지만 아무 웹사이트나 무작정 섞는 것은 아니다. Chromium의 현재 프로세스 모델은 SiteInstance와 ProcessLock 같은 개념으로 어떤 문서와 워커가 어느 렌더러에 들어갈 수 있는지 추적한다.[4] 같은 탭 안에서도 보안 경계가 다르면 별도 렌더러가 필요할 수 있다.

렌더러가 멈추거나 충돌하면 탭의 내용이 깨질 수 있다. 그러나 주소창과 다른 사이트의 렌더러가 별도 프로세스에 있다면 영향을 국소화할 여지가 생긴다. 이것이 ‘탭을 여러 프로세스로 만든다’기보다 ‘웹 콘텐츠를 권한 낮은 여러 실행 구역에 배치한다’고 이해해야 하는 이유다.

탭은 사용자가 보는 묶음이고,
프로세스는 브라우저가 지키는 경계다.

05 / A SITE-SHAPED SECURITY BOUNDARY

탭보다 사이트 경계가 중요하다

초기의 멀티프로세스 브라우저를 ‘탭마다 프로세스 하나’라고 설명하면 대략적인 감은 잡을 수 있다. 하지만 현대 Chromium의 중요한 보안 원리는 사이트 격리다. 렌더러 프로세스를 특정 사이트의 문서와 워커에 잠그고, 교차 사이트 데이터가 잘못된 렌더러로 넘어가지 않도록 브라우저 프로세스가 추가 검사를 한다.

공식 프로세스 모델 문서는 데스크톱의 전체 사이트 격리 모드에서 각 프로세스가 한 사이트의 문서에 잠긴다고 설명한다. 같은 출처 정책의 ‘origin’과 프로세스 배치에 쓰이는 ‘site’는 완전히 같은 단위가 아니다. scheme과 등록 가능한 도메인 등 Chromium의 SiteInfo 계산이 관여한다.[4]

왜 이런 선이 필요한가. 렌더링 엔진 취약점으로 한 렌더러의 코드 실행을 빼앗겼다고 가정해도, 다른 사이트의 민감한 문서가 같은 주소 공간에 없다면 직접 훔쳐볼 수 있는 범위를 줄일 수 있다. Chromium의 보안 문서는 샌드박스와 IPC 검사, 사이트 격리가 손상된 렌더러가 할 수 있는 일을 함께 제한한다고 설명한다.[5]

사이트 격리는 브라우저가 모든 공격을 막는 마법막이 아니다. 브라우저 프로세스의 검증 결함, 운영체제 취약점, 잘못된 권한 허용, 같은 사이트 안의 웹 취약점은 별도의 문제다. 다만 한 사이트를 처리하던 방이 무너졌을 때 곁방의 비밀까지 자동으로 열리지 않도록 벽을 하나 더 세운다.

06 / ONE PAGE, MORE THAN ONE ROOM

한 페이지 안에서도 방이 갈린다

뉴스 페이지 하나가 광고, 동영상, 결제 위젯을 서로 다른 사이트의 iframe으로 불러온다고 해 보자. 화면에는 직사각형 하나 안에 모두 붙어 있지만 보안상 같은 문서가 아니다. 전체 사이트 격리에서는 교차 사이트 하위 프레임이 별도 렌더러 프로세스에 놓일 수 있다. 이를 out-of-process iframe, 줄여서 OOPIF라고 부른다.

이때 부모 페이지와 iframe은 같은 메모리에서 함수를 부르듯 통신하지 않는다. 브라우저가 프레임 트리와 탐색을 조정하고, 허용된 웹 표준 메시지와 합성 결과를 경계를 넘어 연결한다. Chromium은 각 RenderFrameHost의 SiteInstance를 추적해 사용할 렌더러를 결정한다.[4]

그래서 탭 하나가 렌더러 하나라는 등식은 깨진다. 교차 사이트 iframe이 세 개라고 반드시 렌더러가 정확히 세 개 더 생긴다고도 말할 수 없다. 같은 사이트 인스턴스의 공유 가능성, 관련 탭, 프로세스 한도와 플랫폼 정책이 배치에 영향을 준다. 보안상 필요한 격리는 유지하되 구체적인 수는 구현과 상황이 결정한다.

화면 합성은 더 흥미롭다. 여러 렌더러가 자기 프레임의 결과를 만들면 브라우저와 Viz/GPU 쪽이 올바른 위치와 쌓임 순서로 조합한다. 사용자는 매끈한 페이지 하나를 보지만 그 픽셀은 여러 격리 구역의 협업 결과일 수 있다.

07 / SPECIALIZED SERVICES

네트워크와 GPU도 따로 움직인다

웹페이지는 네트워크와 그래픽 장치를 필요로 하지만 렌더러가 이 자원을 제한 없이 직접 다루게 할 필요는 없다. Chromium의 네트워크 서비스는 요청, 연결, 프록시, 캐시와 관련된 기능을 서비스로 분리한다. 공식 문서는 네트워크 서비스를 브라우저 프로세스 안에서도, 별도 유틸리티 프로세스에서도 실행할 수 있게 설계했으며 대부분의 플랫폼에서는 격리와 안정성을 위해 프로세스 밖 구성이 기본이라고 설명한다.[6]

GPU/Viz 프로세스는 여러 렌더러가 만든 합성 자료를 받아 디스플레이에 표시하는 경로를 담당한다. GPU 드라이버는 복잡하고 브라우저 전체가 공유하는 자원이므로 전용 프로세스에 두면 렌더러마다 드라이버 상태를 중복하지 않고, 문제를 별도 경계에서 관리할 수 있다. RenderingNG 문서는 Viz 프로세스 안의 GPU 주 스레드와 디스플레이 합성 스레드를 설명한다.[7]

확장 프로그램, 오디오, PDF, 데이터 디코더 같은 기능도 별도 렌더러나 유틸리티 프로세스에서 동작할 수 있다. 구체적인 분해는 버전과 플랫폼에 따라 바뀐다. ‘Chrome은 언제나 브라우저 1개, GPU 1개, 네트워크 1개, 탭당 렌더러 1개’라는 고정 도표는 이해를 돕는 순간 그림일 뿐 계약이 아니다.

서비스화의 장점은 권한과 생명주기를 기능별로 다르게 줄 수 있다는 점이다. 네트워크 서비스가 필요한 네트워크 권한과 이미지 디코더가 필요한 권한은 같지 않다. 작은 서비스 경계를 만들면 각자가 가져야 할 능력만 주고, 충돌했을 때 다시 시작할 대상을 좁힐 수 있다.

08 / WALLS NEED RULES

분리만으로 안전해지지는 않는다

서로 다른 프로세스에 넣었다고 자동으로 안전한 것은 아니다. 자식 프로세스가 운영체제의 모든 파일과 장치에 접근할 수 있다면 주소 공간만 다른 강한 프로그램 여러 개가 생긴다. 샌드박스는 렌더러 같은 대상 프로세스의 권한을 낮추고, 허용된 작업을 브라우저 같은 broker가 정책에 따라 대신 수행하게 한다.

Chromium의 샌드박스 설계 문서는 프로세스 수준의 broker와 target을 구분한다. 브라우저 프로세스가 정책을 지정하고 샌드박스 대상 프로세스를 만들며, 렌더러는 일반적으로 target이 된다.[8] 운영체제별 구현은 다르지만 ‘믿지 않는 코드를 낮은 권한의 별도 프로세스에 둔다’는 목적은 같다.

IPC도 검문소가 된다. 렌더러가 “이 파일을 열어 달라”거나 “이 탐색을 확정해 달라”고 메시지를 보냈다고 브라우저가 그대로 수행하면 안 된다. 메시지의 형식, 현재 문서의 권한, 출처와 사용자 동작을 다시 확인해야 한다. 경계는 벽뿐 아니라 문을 통과하는 규칙까지 포함한다.

명령행의 --no-sandbox 같은 선택은 편의상 문제를 숨길 수 있지만 이 경계를 약화한다. 웹에서 본 해결법을 이유도 모른 채 적용하면 ‘페이지가 열린다’는 결과와 맞바꿔 보호 장치를 끌 수 있다. 샌드박스 오류는 원인을 고쳐야지 안전장치를 없애 정상 상태로 부르면 안 된다.

프로세스를 나눈다는 것은 일을 복제하는 것이 아니라,
실패와 권한이 넘어갈 선을 그리는 일이다.

09 / LET ONE FAILURE STAY SMALL

한 탭의 실패가 창 전체를 삼키지 않게

모든 웹 콘텐츠가 브라우저 프로세스 안에서 실행되면 렌더링 엔진의 잘못된 메모리 접근 하나가 주소창, 다른 탭과 다운로드까지 함께 종료시킬 수 있다. 렌더러를 분리하면 해당 프로세스가 충돌했을 때 그 프로세스가 담당하던 문서에 실패를 표시하고, 브라우저 UI와 다른 렌더러는 남길 수 있다.

Chromium의 안정성 문서는 브라우저, 렌더러와 GPU 프로세스 등 서로 다른 충돌 유형을 구분해 다룬다.[9] GPU 프로세스나 네트워크 서비스처럼 다시 시작 가능한 구성요소는 복구 전략을 따로 설계할 수 있다. 분리는 실패가 없게 만드는 것이 아니라 실패의 반경을 줄이고 복구 단위를 만든다.

그러나 두 탭이 같은 렌더러를 공유한다면 하나의 렌더러 충돌이 둘 모두에 영향을 줄 수 있다. 한 탭 안의 여러 프레임도 서로 다른 렌더러를 쓸 수 있다. ‘렌더러 충돌 = 정확히 탭 하나만 실패’라는 문장도 항상 맞지는 않는다. 실제 영향 범위는 당시의 프로세스 배치에 달렸다.

브라우저 프로세스 자체가 충돌하면 조정자와 UI가 사라져 창 전체가 닫힐 수 있다. 그래서 더 많은 프로세스가 보인다는 사실은 모든 실패가 완벽하게 격리됐다는 보증이 아니라, 중요한 실패를 가능한 작은 구역에 가두려는 설계의 흔적이다.

10 / ISOLATION HAS A PRICE

격리에는 메모리 비용이 든다

프로세스마다 주소 공간, 힙, 스택, IPC 채널과 관리 구조가 필요하다. 같은 라이브러리의 읽기 전용 페이지는 운영체제가 공유할 수 있어도 모든 상태가 공짜로 합쳐지는 것은 아니다. 렌더러를 더 세밀하게 나누면 한 프로세스에 몰아넣을 때보다 기본 메모리 비용과 통신 횟수가 늘 수 있다.

반대로 한 프로세스에 모든 탭을 넣으면 메모리 수치가 작아 보일 수 있지만, 충돌 반경과 보안 위험, 한 작업이 다른 작업을 막는 문제가 커진다. 프로세스 수를 줄이는 것이 전체 성능을 항상 개선하는 것도 아니다. 여러 CPU 코어에서 병렬로 실행하거나, 사용하지 않는 렌더러를 개별적으로 정리할 기회도 분리에서 나온다.

Chromium의 프로세스 모델은 무제한으로 렌더러를 만드는 대신 프로세스 한도와 재사용 정책을 둔다. 공식 문서는 한도에 도달하면 같은 사이트의 기존 프로세스를 공유할 수 있는 예를 들면서도, 사이트 격리에 필요한 경우 한도를 넘어 새 프로세스를 만들 수 있다고 설명한다.[4] 보안 경계와 자원 제약 사이의 타협이다.

메모리가 부족하면 브라우저는 백그라운드 탭의 작업을 줄이거나 문서를 버리고 나중에 다시 불러오는 정책을 사용할 수 있다. 따라서 작업 관리자의 프로세스 수만 세어 ‘낭비’를 판단하기보다 각 프로세스의 메모리·CPU 사용량, 맡은 작업, 탭의 수명과 실제 체감 문제를 함께 봐야 한다.

11 / WHY THE COUNT KEEPS CHANGING

탭 수로 프로세스 수를 계산할 수 없는 이유

새 탭을 열 때 렌더러가 새로 생길 수도 있고 기존 렌더러를 공유할 수도 있다. 같은 탭의 교차 사이트 iframe 때문에 렌더러가 더 생길 수도 있다. 확장 프로그램, 서비스 워커, GPU와 네트워크 서비스가 별도 항목으로 보일 수 있으며, 사용하지 않는 프로세스가 잠시 남거나 메모리 압박으로 정리될 수도 있다.

관련 탭의 스크립트 연결, 사이트 격리 수준, 브라우저 프로필, 확장 프로그램, 플랫폼과 버전도 영향을 준다. 하나의 렌더러가 여러 탭을 담당할 수 있고, 하나의 탭이 여러 렌더러를 사용할 수 있다. 그러므로 ‘탭 3개니까 브라우저 1 + GPU 1 + 렌더러 3 = 5’ 같은 산식은 학습용 예시일 뿐 실제 진단 공식이 아니다.

작업 관리자에서 같은 이름의 프로세스가 늘어난 순간만 보고 바이러스로 단정하거나 모두 강제 종료하면 작성 중인 데이터와 세션을 잃을 수 있다. Chrome Enterprise 도움말은 운영체제 도구의 --type=renderer 같은 명령행 인자나 Chrome 작업 관리자를 통해 프로세스 유형과 사용량을 식별하라고 안내한다.[10]

이상 여부는 숫자보다 행동으로 본다. 특정 탭을 닫았을 때 CPU 사용이 내려가는지, 확장 프로그램을 끄면 반복 문제가 사라지는지, 어떤 프로세스가 지속적으로 자원을 소비하는지 확인한다. 프로세스가 많다는 것은 진단의 시작점이지 결론이 아니다.

12 / FOLLOW THE REQUEST

요청 하나가 어느 방을 지나는지 따라가자

아래 체험은 브라우저의 실행 경계를 단순화한 흐름도다. 주소 탐색, 교차 사이트 iframe 표시, 렌더러 충돌과 파일 선택 요청을 고르면 관련 역할이 차례로 강조된다. 실제 Chromium의 스레드, IPC 메시지와 모든 중간 단계를 재현하지 않으며 프로세스 개수도 계산하지 않는다.

‘다음 경계’를 누를 때마다 누가 결정을 내리고, 누가 낮은 권한에서 콘텐츠를 처리하며, 어느 지점에서 결과가 합쳐지는지 살펴보자. 중요한 것은 모든 요청이 같은 권한으로 직진하지 않는다는 점이다. 브라우저 프로세스가 조정하고 전문 서비스와 렌더러가 제한된 역할을 나눠 맡는다.

13 / OBSERVE WITHOUT OVERREADING

직접 확인하되 숫자를 오해하지 말자

데스크톱 Chrome에서는 메뉴의 도구 영역이나 Shift+Esc로 Chrome 작업 관리자를 열어 탭, 하위 프레임, 확장 프로그램과 GPU 작업의 자원 사용을 볼 수 있다. Site Isolation 공식 페이지도 작업 관리자에서 하위 프레임 프로세스를 확인하는 방법을 안내한다.[11] 운영체제 작업 관리자는 프로세스 ID와 전체 자원 사용을 보는 데 유용하다.

실험은 안전하게 작게 한다. 빈 프로필이나 중요하지 않은 탭에서 서로 다른 사이트 두 개와 같은 사이트 두 개를 열고, Chrome 작업 관리자의 항목을 비교한다. 교차 사이트 iframe이 있는 페이지에서는 ‘Subframe’ 항목이 보일 수 있다. 다만 같은 버전과 같은 탭에서도 즉시 같은 수가 나온다고 보장하지 말고 관찰 시점과 환경을 기록한다.

특정 항목의 CPU가 높다면 페이지를 닫기 전에 작업 내용을 저장하고, 탭·확장·GPU 중 무엇인지 식별한다. 강제 종료는 원인을 좁힌 뒤 선택할 마지막 조치다. 브라우저 프로세스나 GPU 프로세스를 운영체제에서 임의로 끝내면 여러 탭이나 전체 창에 영향을 줄 수 있다.

chrome://sandbox와 내부 진단 페이지는 브라우저 버전과 정책에 따라 정보를 보여 줄 수 있지만, 보안 설정을 바꾸는 명령이 아니다. 관찰과 변경을 구분하고, 인터넷에서 본 플래그를 이유 없이 적용하지 않는다. 이 글의 목표는 프로세스 수를 줄이는 요령이 아니라 그 수가 생긴 구조를 읽는 법이다.

14 / A MAP OF TRUST BOUNDARIES

많은 프로세스는 경계의 지도다

모눈 사무실의 창 하나 뒤에 열두 프로세스가 있었던 이유는 브라우저가 열두 번 켜졌기 때문이 아니다. 주소창과 권한을 가진 브라우저 프로세스, 낯선 웹 코드를 실행하는 렌더러, 사이트 경계가 다른 하위 프레임, 네트워크와 GPU 같은 전문 서비스가 서로 다른 책임과 권한으로 움직였기 때문이다.

프로세스 분리는 오류를 없애지 않는다. 한 렌더러는 여전히 멈출 수 있고, GPU 프로세스는 충돌할 수 있으며, 브라우저 프로세스의 잘못은 큰 영향을 준다. 다만 실패와 침해가 곧장 모든 탭과 운영체제로 번지지 않도록 반경을 줄이고, 다시 시작하거나 차단할 단위를 만든다.

그 대가로 메모리와 IPC 비용을 낸다. 그래서 브라우저는 무조건 탭마다 새 프로세스를 만드는 단순 규칙 대신 사이트 격리, 관련 문서, 프로세스 한도와 플랫폼 조건을 함께 본다. 실제 숫자가 계속 바뀌는 것은 구조가 무질서해서가 아니라 경계와 비용을 그때그때 조정하기 때문이다.

다음에 작업 관리자에서 같은 브라우저 이름이 길게 늘어서 있으면 숫자만 지우려 하지 말자. 어느 줄은 낯선 웹 코드를 가둔 방이고, 어느 줄은 여러 탭이 공유하는 그래픽 작업실이며, 어느 줄은 강한 권한을 대신 행사하는 조정자다. 하나의 창이 하나의 권한으로 움직이지 않는다는 사실이 바로 현대 브라우저가 스스로를 지키는 방식이다.

많은 프로세스는 혼란의 목록이 아니라,
